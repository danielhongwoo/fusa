# 18장 근거 문서에서 뽑은 사실 (읽기 기록)

대상: 18장 "변경, 형상, 릴리스 이후" (plans/ch18-change-and-configuration.md). 읽은 날: 2026-11-23.

- 쪽 칸은 PDF 파일의 몇 번째 쪽이다. 문서에 인쇄된 쪽 번호가 다르면 절 머리에 차이를 적는다.
- 인용은 줄바꿈을 합치고 따옴표와 줄표를 ASCII로 바꿨다. 그 밖에는 원문 그대로다. Ariane 501 보고서는 스캔본이라 OCR (tesseract)로 읽었고, 또렷하게 읽힌 구절만 인용했다. 이 문서의 줄은 tools/quotecheck.py가 건너뛴다.
- 이 장의 규격 문서 (ISO 26262, IEC 61508, UN R156, ISO 24089)는 받지 못했다. 이 파일의 사실은 모두 받은 문서가 말한 것이다.
- 사고 조사 보고서의 줄은 "조사 기관의 결론 / 권고 / 관찰"을 사실 칸에 가려 적었다. b737max-house-report는 의회 위원회의 보고서이고, b737max-jatr는 여러 항공 당국이 모인 검토 팀의 보고서다.
- `(기억)`은 문서에서 확인하지 못한 내용이다. 원고의 근거로 쓰지 않는다. 맨 끝의 "문서에서 찾지 못한 것" 절에만 둔다.
- 원고에 쓰기 전에 그 쪽을 직접 열어 확인한다 (RULES.md 5.2절).

## 문서에서 찾지 못한 것

- over-the-air update, 소프트웨어 갱신 중의 전원 상실, bootloader, 호환 검사, 되돌리기: 받은 문서의 읽은 쪽에 없다. NASA 지침서의 roll back은 SCM의 version 관리에서 이전 판으로 되돌리는 것이고 (F18-026), COTS upgrade에서 "실패하면 어떻게 되는가"의 질문 (F18-054)이 가장 가깝다. 갱신 장치의 설계는 받은 문서에 없다.
- UN R156, ISO 24089 (소프트웨어 갱신 관리 체계의 규제와 규격): 받지 못했다. (기억) UN R156은 차량의 소프트웨어 갱신 관리 체계를 형식 승인의 대상으로 삼고, ISO 24089는 소프트웨어 갱신 공학의 규격이다.
- CI (continuous integration), host test의 자동 실행: 받은 문서에 없다. NASA-GB는 SCM의 지표와 regression testing (F18-015, F18-050)을 말하지만 자동화한 build 흐름은 없다. NASA-STD의 SWE-191 (F18-065)이 regression testing의 요구다.
- 생산과 서비스 단계, 폐기 단계의 안전: NASA-STD-8739.8B의 폐기 (retirement) 요구 (F18-067, F18-071)와 NHTSA 보고서의 "manufacturing defects" 요구사항 (읽은 90쪽의 요구사항 3) 말고는 없다. NASA 지침서 10장은 운영과 유지보수까지만 다룬다. (기억) ISO 26262-7이 생산, 운영, 서비스, 폐기를 다룬다.
- field monitoring: NASA 지침서에는 비행 중 이상의 분석 (F18-051), JATR에는 MSAD의 in-service data (F18-094)가 있다. 소프트웨어 기능의 field monitoring 체계를 직접 서술한 곳은 읽은 쪽에 없다.
- calibration data와 configuration data를 소프트웨어 안전의 관점에서 다룬 서술: NHTSA 보고서의 요구사항 (F18-118, F18-121)과 NASA-STD의 SWE-193 (F18-066)이 전부다. calibration 값이 안전 요구사항을 깨뜨릴 수 있다는 서술과 범위 검사는 읽은 쪽에 직접 있지 않다. 예제의 최대 토크 parameter에 관한 근거는 문서에서 찾지 못했다.
- baseline의 정의: NASA-STD의 Configuration Item 정의 (F18-063)가 baselined를 쓰고, NASA 지침서는 baseline product (F18-017)와 requirements baseline (F18-038)을 쓴다. baseline 자체를 정의한 문장은 읽은 쪽에 없다.
- ISO 26262-8과 IEC 61508-1의 변경 관리와 형상 관리 조항: 받지 못했다.
- 반복적 개발에서의 safety lifecycle: NASA 지침서의 2004년의 판단 (agile을 권하지 않음, F18-012)과 lifecycle 모델 서술 (F18-001 - F18-015)뿐이다. agile을 safety case와 함께 쓰는 현대의 방법은 받은 문서에 없다.
- Ariane 501 보고서의 권고 번호 R1 - R3: 17쪽의 OCR이 번호를 "Rl R4 R5 ..."로 일부만 읽어서 문단 순서로 맞췄다 (F18-114). 원고에 쓰기 전에 쪽 그림으로 확인한다.
