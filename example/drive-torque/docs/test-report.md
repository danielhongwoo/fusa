# test 보고서

2026-11-23에 `make check`와 `make mutation`을 돌린 결과를 옮겨 적은 것이다. 단계 1의 코드에 단계 2의 구현 둘을 더한 상태다: 허용 토크가 오르는 속도의 상한 (`SWR-13`)과 간헐 고장의 판정 (`SWR-14`). 이 문서는 자동으로 만들어지지 않는다. 다시 돌린 결과는 `build/reports/` 아래에 생기고, 숫자가 이 문서와 다르면 `build/reports/`가 맞다.

- 환경: macOS (arm64), Apple clang (빌드와 test), GCC 16.2 (coverage), cppcheck 2.22, clang-tidy (LLVM 23), CBMC 6.11.
- 깨끗한 container에서는 돌려 보지 못했다.
- 이 도구들은 어느 것도 qualification되지 않았다.
- 시뮬레이션의 결과다. 보이는 것은 논리이고, 하드웨어의 동작이 아니다.

## 3. fault injection

fault는 HAL의 뒤에서 넣거나, 기능 모듈을 결함이 있는 것으로 바꿔 끼워서 넣었다. `FI-01`과 `FI-02`는 넣는 시각을 10 ms 주기 안에서 0-9 ms로 바꿔 가며 가장 나쁜 시간을 쟀다. `FI-07`은 끊김의 주기 80 ms 안에서 10 ms씩 옮겨 가며 쟀다.

| ID | fault | 넣는 곳 | 결과 | 잰 시간 (가장 나쁜 경우) |
|---|---|---|---|---|
| `FI-01` | 페달 채널 1이 높은 값에 고착 | HAL | 페달 고장으로 판정하고 토크 0, 경고. 판정 전에도 출력은 낮은 채널을 따랐다. 기능 고장의 고정은 없었다 | 토크 요구 0까지 29 ms (한계 30). 모터의 토크가 5% 아래로 내려갈 때까지 88 ms (예산 92) |
| `FI-02` | 주행 중에 기능이 100 Nm 더 큰 토크를 요구 | 결함 모듈 | 넘는 토크는 한 주기도 나가지 않았다. 고정하고 토크 0, 구동 허용 차단, 경고 | 고정과 차단까지 49 ms (한계 50). 모터의 토크가 5% 아래로 내려갈 때까지 108 ms (예산 111) |
| `FI-03` | 센서의 전원이 20% 올라가 두 채널이 함께 올라감 | HAL | 알아채지 못했다. 페달 30%를 38.5%로 읽었고 토크가 따라 올라갔다 | - |
| `FI-04` | 페달을 놓고 서 있는데 기능이 30 Nm를 요구 | 결함 모듈 | 출력은 계속 0이고 차는 움직이지 않았다. 5주기 뒤에 고정했다 | 고정까지 50 ms 안 |
| `FI-05` | 기능이 토크를 절반만 냄 | 결함 모듈 | 알아채지 못했다. 허용 범위 안이므로 그대로 나갔다 | - |
| `FI-06` | 후진 중에 기능이 최대 토크를 요구 | 결함 모듈 | 출력은 후진의 허용 토크 (35 Nm)를 넘지 않았다. 고정하고 차단했다 | 고정까지 50 ms 안 |
| `FI-07` | 페달을 끝까지 밟은 채 채널 1이 80 ms마다 한 주기씩 끊기고, 그 중에 기능이 최대 토크를 요구 | HAL과 결함 모듈 (fault 둘) | 선이 끊기기만 할 때는 깎이지 않았고 페달 고장으로 판정하지도 않았다. 기능의 결함을 켜자 그 주기부터 깎였다. 나간 토크가 정상인 기능의 토크를 55 Nm 넘게 앞선 때가 없었다 | 고정과 차단까지 40 ms |
| `FI-08` | 페달을 30% 밟은 채 채널 1이 80 ms마다 한 주기씩 끊김. 기능은 정상 | HAL | 끊긴 주기마다 토크가 0으로 떨어졌다가 다시 올랐다 (판정 전에 10번). 그동안 토크는 실제 페달 위치의 허용 토크를 넘지 않았다. 11번째로 끊긴 주기에 페달 고장으로 판정하고 토크 0, 경고. 구동 허용 신호는 끊지 않았다 | 처음 끊긴 때부터 판정까지 800 ms |

차량 수준 (`SG-01`). 고장이 없을 때 같은 입력에서 나오는 가속과 견주었다.

| 경우 | 가속의 차이가 가장 클 때 | 1.0 m/s^2를 넘은 시간 | `SG-01` |
|---|---|---|---|
| `FI-02`, 감시 있음 | 0.08 m/s^2 | 0 ms | 지켰다 |
| `FI-06`, 감시 있음 | 0.08 m/s^2 | 0 ms | 지켰다 |
| `FI-07`, 감시 있음 | 0.00 m/s^2 | 0 ms | 지켰다 |
| `NC-001`: `FI-02`와 같은 fault, 감시를 뺌 | 1.81 m/s^2 | 984 ms (시나리오가 끝날 때까지) | 어겼다 |

- `NC-001`은 대조다. 감시와 출력 단계를 아무것도 하지 않는 모듈로 바꿔 끼웠다. 이 fault를 막지 않으면 `SG-01`을 어긴다는 것을 보인다. 그래서 위의 0.08은 감시가 한 일이다.
- 처음의 `FI-02`는 30 Nm를 더했다. 그 크기는 감시가 없어도 0.54 m/s^2여서 `SG-01`을 어기지 않는다. 감시가 있든 없든 통과하는 판정이었다. 단계 검토에서 찾아 100 Nm로 고치고 대조를 더했다.
- `FI-07`은 fault가 둘 겹친 경우다. 단계 1의 감시 (페달에서 나온 상한만 본다)로는 이 경우에 `SG-01`을 어겼다. 페달이 100%이면 상한이 최대 토크여서 깎을 것이 없다. 변이 검사에서 오르는 속도를 제한하는 줄을 빼면 `TC-205`가 실패한다.
- 이 값들은 가정한 plant model (질량, 기어비, inverter의 응답)에서 나온 것이다.

`FI-03`과 `FI-05`는 통과가 "알아채지 못한다"인 test다. 감시의 한계를 기록으로 남기려는 것이다.

- `FI-03`: 두 채널이 맞으면 믿는 검사는 둘이 함께 틀리는 것을 잡지 못한다. 가정 `A-02`가 이것을 막는다.
- `FI-05`: 토크가 모자라는 것은 `SG-01` 밖이다. 감시는 상한만 본다.

- GCC의 `-fcondition-coverage`와 `gcov --conditions`로 쟀다. GCC가 재는 것은 masking MC/DC다.
- 최적화를 끈 빌드 (`-O0`)의 source 수준 측정이다. 제품에 실릴 기계어를 잰 것이 아니다.

## 5. 증명

CBMC로 [../test/proof/harness.c](../test/proof/harness.c)의 성질을 증명했다. 모든 32-bit 입력에 대해서다.

| 성질 | 내용 |
|---|---|
| 1 | 허용 토크는 0 이상 최대 토크 이하다. 0이어야 하는 조건에서는 0이다. 후진에서는 105 Nm 이하다 |
| 2 | 깎은 토크는 허용 토크 안에 있고, 방향은 기어를 따른다 |
| 3 | 출력 단계는 어떤 상태에서 시작해도 허용 토크 안의 값을 낸다. 고정은 풀리지 않고, 고정되면 0이다 |
| 4 | 안전한 페달 값은 0-1000이다. 페달 고장은 풀리지 않고, 고장이거나 켠 직후면 0이다. 최근 주기들의 기록에 실패가 10번을 넘게 있으면 고장이다. 기록과 적을 자리가 어떤 값이어도 (memory의 값이 틀려도) 배열 밖을 쓰지 않는다 |
| 5 | 오르는 속도를 제한한 허용 토크는 페달에서 나온 상한을 넘지 않고, 지난 주기에 보낸 토크의 크기에서 25 Nm 넘게 오르지 않는다. 지난 출력이 어떤 값이어도 계산이 넘치지 않는다 |
| 6 | 정상인 기능의 토크 요구는 깎이지 않는다. 기능의 지난 요구와 출력 단계의 지난 출력이 같은 상태에서 시작하면, 입력이 무엇이든 한 주기 뒤에도 그 상태이고 토크 요구는 그대로 나간다. 켠 직후가 그 상태다. 허용 토크는 토크 요구를 5 Nm 넘게 앞서지 않는다 |

- 계산 중의 signed overflow, 0으로 나누기, 값이 잘리는 형 변환, 배열 밖의 접근이 없다는 것도 함께 증명했다. 반복문은 101번까지 펼쳤고, 그보다 길게 도는 반복이 없다는 것도 확인했다.
- 증명한 것은 C 코드의 논리다. compiler가 만든 기계어, 실행 시간, 하드웨어의 고장, 주기를 놓치는 경우는 덮지 않는다.
- 성질 1 - 5는 함수 하나의 한 주기에 대한 것이다. 여러 주기에 걸친 동작 (예: 5주기 뒤에 고정)은 test로 본다.
- 성질 6은 기능, 감시, 출력 단계를 제품과 같은 순서로 이은 한 주기의 걸음이다. 시작 상태와 걸음을 함께 증명했으므로 몇 주기를 돌아도 성립한다. 전제가 있다: 기능과 감시가 같은 주기에 같은 입력을 받고, 주기마다 한 번씩 순서대로 실행되고, 두 모듈의 변수를 다른 코드가 바꾸지 않는다.
- 성질 5와 6은 상수가 어긋나면 실패한다. 감시의 값을 24.9 Nm로 바꾸면 성질 6이, 25.1 Nm로 바꾸면 성질 5가, 기능의 값을 25.1 Nm로 바꾸면 성질 6이 실패하는 것을 확인했다.
- 성질 4는 "안전한 페달 값이 운전자가 밟은 것보다 크지 않다"를 증명하지 않는다. 그것은 센서에 대한 가정에서 나온다.

## 6. 만드는 동안 찾은 것

| 찾은 수단 | 찾은 것 | 조치 |
|---|---|---|
| CBMC | 전압을 페달 위치로 바꿀 때 `mv - min_mv`를 먼저 계산했다. HAL이 범위 밖의 값을 주면 signed overflow가 난다. 그때 test는 모두 통과하고 있었다 | 빼기 전에 범위를 보도록 고쳤다 |
| coverage | 입력 읽기의 MC/DC가 42%였다. 기어 값을 알 수 없는 경우의 test가 없었다 | `TC-107`을 더했다 |
| clang-tidy | 기능의 코드에 같은 내용의 분기가 둘 있었다 | 조건을 합쳤다 |
| cppcheck (MISRA 검사) | 변수 이름 `pedal`을 규칙 7.3 위반으로 낸다 | 거짓 경보다. 기록만 했다 (`notes/tool-check.md`) |
| 단계 검토 (FuSa 전문가) | 감시의 허용 토크가 정상 동작보다 훨씬 큰 운전 상태가 있었다 (후진, 높은 속도). 거기에서 기능이 틀리면 감시를 지나 `SG-01`을 어긴다. coverage 100%, 증명 4개, 변이 10개가 모두 통과한 뒤였다 | 틈의 조건을 요구사항으로 만들고 (`SWR-06`), 기능과 감시를 고치고, `TC-007`, `TC-011`, `TC-204`를 더했다 |
| 단계 검토 (임베디드 엔지니어) | 변이 21개를 더 넣자 test가 4개를 놓쳤다. test의 기댓값이 제품의 상수 이름을 쓰고 있어서, 상수가 바뀌면 기댓값도 따라 바뀌었다. MC/DC는 100%였다 | 기댓값을 요구사항의 숫자로 바꾸고, test를 더하고, 변이를 36개로 늘렸다 |
| 변이 검사 도구 | "잡았다"고 센 변이 하나가 실은 compile되지 않는 것이었다 | compile 실패를 따로 세도록 도구를 고쳤다 |
| 단계 검토 2차 (두 검토자가 따로) | 기능이 제동 우선이 걸린 상태를 기억했다. 브레이크를 놓아도 가속 페달을 놓을 때까지 토크 0을 냈다. 감시는 그 상태를 모르므로 그동안 허용 토크 전부 (페달 80%에서 205 Nm)가 틈이었다. 틈을 보는 `TC-007`의 격자에는 브레이크를 밟았다 놓는 순서가 없었다 | 기능에서 그 상태를 뺐다. `TC-011`을 입력이 바뀌는 경우 열 가지로 넓혔다. 새 `TC-011`은 고치기 전의 기능에서 실패한다 |
| 진행자의 실험, 단계 검토 3차 | 입력이 70 ms보다 빨리 거듭 바뀌면 정상인 기능이 토크를 다 올리지 못해 틈이 이어진다. 브레이크 신호가 80 ms마다 한 주기씩 튀는 경우에 기능이 허용 토크까지 요구하면, 4000 ms 가운데 3995 ms 동안 가속의 차이가 1.0 m/s^2를 넘는다 (가정한 inverter의 응답으로 계산). 페달 한 채널의 간헐 단선도 같은 모양을 만들고, 입력 검사는 판정하지 못한다. 처음에 진행자는 이것을 토크 요구로만 보고 "10 ms의 틈을 두고 이어진다"고 적었다. 검토자가 차량의 가속으로 다시 쟀다 | 단계 1에서는 고치지 않고 한계로 적었다. 단계 2에서 감시의 허용 토크가 오르는 속도에 상한을 두어 닫았다 (`SWR-13`). 실험은 `TC-013`과 `FI-07`이 되었다 |
| 단계 2의 설계 토론 (임베디드 엔지니어의 시제품) | 기어가 바뀌는 주기에 페달이 낮으면 기능이 목표보다 큰 토크를 한 주기 냈다 (목표 -19.8 Nm에 -25 Nm). 올리는 속도의 제한이 방향이 바뀐 것을 보지 않고 지난 주기의 토크와 견주었기 때문이다. 감시가 그 한 주기를 깎았다. `SG-01`은 지켜졌지만 "정상인 기능은 깎이지 않는다"가 깨져 있었다. `TC-007`의 격자와 `TC-011`의 열 가지 경우에는 이 입력이 없었다 | 기능을 고쳤다. `TC-011`에 두 경우를 더하고, `TC-007`에 무작위 운전 10만 주기를 더했다 (깎인 주기 0, 목표를 넘은 주기 0). 고치기 전에는 23주기와 32주기였다 |
| 변이 검사 (`SWR-14`를 넣은 직후) | "오래된 실패를 기록에서 지우지 않는다"는 변이를 test가 놓쳤다. 판정하지 않아야 하는 경우의 test가 10주기마다 한 번 실패하는 입력이었는데, 기록의 길이가 100이어서 실패가 늘 같은 열 자리에만 적혔다. 지우지 않아도 열 자리를 넘지 않았다. coverage는 100%였다 | 11주기마다 한 번 실패하는 입력을 더했다. 실패가 자리를 옮겨 가며 적히므로, 지우지 않으면 쌓여서 고장이 된다 |

단계 검토에서 나온 세 줄이 이 표에서 가장 값진 줄이다. 요구사항에 따른 test, coverage 100%, 증명이 모두 통과한 상태에서 다른 눈이 (여기서는 다른 역할의 검토자가) 찾은 것이다.

## 7. 변이 검사

제품 코드에 결함을 하나씩 넣고 `make test`를 돌렸다. 손으로 고른 것 31개와, 상수를 하나씩 1 올린 것 23개다 (안전 요구사항을 받는 파일의 상수 21개, 감시의 한계와 맞물리는 기능의 상수 2개). 54개 모두 test가 실패했다. 손으로 고른 것 가운데 8개는 `SWR-13`의 코드에, 5개는 `SWR-14`의 코드에 넣은 것이다.

동등한 변이가 하나 있다. 이어진 횟수를 한계에서 멈추지 않게 바꿔도 밖에서 보이는 동작이 같다. 어떤 test도 잡을 수 없으므로 이유를 적어 따로 두고, 놓친 것으로 세지 않는다.

- 이것이 보이는 것은 "넣어 본 결함을 잡는다"까지다.
- 처음에는 10개를 넣었고 10개를 잡았다. 그 10개는 test를 쓴 사람이 고른 것이었다. 다른 사람이 21개를 더 넣자 4개를 놓쳤다.

## 8. 하지 않은 것

- 감시 자신이 고장 난 경우의 fault injection (단계 2)
- task를 건너뛰거나 늦게 실행하는 경우 (단계 2. 시뮬레이션의 실행 시간은 0이다)
- CAN 메시지의 손상, 되풀이, 지연 (단계 2)
- 브레이크와 기어 신호의 고장 (단계 2)
- 간헐 고장의 다른 모양. 넣어 본 것은 80 ms마다 한 주기씩 끊기는 경우뿐이다
- reset 뒤의 동작
- 실제 MCU에서의 실행 시간과 stack 사용량
