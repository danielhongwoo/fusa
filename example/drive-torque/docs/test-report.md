- 환경: macOS (arm64), Apple clang (빌드와 test), GCC 16.2 (coverage), cppcheck 2.22, clang-tidy (LLVM 23), CBMC 6.11.
- 깨끗한 container에서는 돌려 보지 못했다.
- 이 도구들은 어느 것도 qualification되지 않았다.
- 시뮬레이션의 결과다. 보이는 것은 논리이고, 하드웨어의 동작이 아니다.

## 3. fault injection

fault는 HAL의 뒤에서 넣거나, 기능 모듈을 결함이 있는 것으로 바꿔 끼워서 넣었다. 넣는 시각을 10 ms 주기 안에서 0-9 ms로 바꿔 가며 가장 나쁜 시간을 쟀다.

| ID | fault | 넣는 곳 | 결과 | 잰 시간 (가장 나쁜 경우) |
|---|---|---|---|---|
| `FI-01` | 페달 채널 1이 높은 값에 고착 | HAL | 페달 고장으로 판정하고 토크 0, 경고. 판정 전에도 출력은 낮은 채널을 따랐다. 기능 고장의 고정은 없었다 | 토크 요구 0까지 29 ms (한계 30). 모터의 토크가 5% 아래로 내려갈 때까지 88 ms (예산 92) |
| `FI-02` | 기능이 30 Nm 더 큰 토크를 요구 | 결함 모듈 | 넘는 토크는 한 주기도 나가지 않았다. 고정하고 구동 허용 신호를 끊고 경고 | 고정과 차단까지 49 ms (한계 50). 모터의 토크가 5% 아래로 내려갈 때까지 108 ms (예산 111) |
| `FI-03` | 센서의 전원이 20% 올라가 두 채널이 함께 올라감 | HAL | 알아채지 못했다. 페달 30%를 38.5%로 읽었고 토크가 따라 올라갔다 | - |
| `FI-04` | 페달을 놓고 서 있는데 기능이 30 Nm를 요구 | 결함 모듈 | 출력은 계속 0이고 차는 움직이지 않았다. 5주기 뒤에 고정했다 | 고정까지 50 ms 안 |
| `FI-05` | 기능이 토크를 절반만 냄 | 결함 모듈 | 알아채지 못했다. 허용 범위 안이므로 그대로 나갔다 | - |

차량 수준 (`SG-01`): `FI-02`에서 고장이 없을 때와 견준 가속의 차이는 가장 클 때 0.08 m/s^2였다. 1.0 m/s^2를 넘은 시간은 0 ms다. 이 값은 가정한 plant model (질량, 기어비, inverter의 응답)에서 나온 것이다.

`FI-03`과 `FI-05`는 통과가 "알아채지 못한다"인 test다. 감시의 한계를 기록으로 남기려는 것이다.

- `FI-03`: 두 채널이 맞으면 믿는 검사는 둘이 함께 틀리는 것을 잡지 못한다. 가정 `A-02`가 이것을 막는다.
- `FI-05`: 토크가 모자라는 것은 `SG-01` 밖이다. 감시는 상한만 본다.

| `src/app/app.c` | 100% (36줄) | 100% (34) | 100% (34개) |

- GCC의 `-fcondition-coverage`와 `gcov --conditions`로 쟀다. GCC가 재는 것은 masking MC/DC다.
- 최적화를 끈 빌드 (`-O0`)의 source 수준 측정이다. 제품에 실릴 기계어를 잰 것이 아니다.
- 100%는 test가 모든 요구사항을 검증했다는 뜻이 아니다. 요구사항에 따라 만든 test가 코드를 빠짐없이 실행했다는 뜻이다.

## 5. 증명

CBMC로 [../test/proof/harness.c](../test/proof/harness.c)의 성질을 증명했다. 모든 32-bit 입력에 대해서다.

| 성질 | 내용 |
|---|---|
| 1 | 허용 토크는 0 이상 최대 토크 이하다. 0이어야 하는 조건에서는 0이다 |
| 2 | 깎은 토크는 허용 토크 안에 있고, 방향은 기어를 따른다 |
| 3 | 출력 단계는 어떤 상태에서 시작해도 허용 토크 안의 값을 낸다. 고정은 풀리지 않고, 고정되면 0이다 |
| 4 | 안전한 페달 값은 0-1000이다. 페달 고장은 풀리지 않고, 고장이거나 켠 직후면 0이다 |

- 계산 중의 signed overflow, 0으로 나누기, 값이 잘리는 형 변환이 없다는 것도 함께 증명했다.
- 증명한 것은 C 코드의 논리다. compiler가 만든 기계어, 실행 시간, 하드웨어의 고장, 주기를 놓치는 경우는 덮지 않는다.
- 증명은 함수 하나의 한 주기에 대한 것이다. 여러 주기에 걸친 동작 (예: 5주기 뒤에 고정)은 test로 본다.

## 6. 만드는 동안 찾은 것

| 찾은 수단 | 찾은 것 | 조치 |
|---|---|---|
| CBMC | 전압을 페달 위치로 바꿀 때 `mv - min_mv`를 먼저 계산했다. HAL이 범위 밖의 값을 주면 signed overflow가 난다. 그때 test는 모두 통과하고 있었다 | 빼기 전에 범위를 보도록 고쳤다 |
| coverage | 입력 읽기의 MC/DC가 42%였다. 기어 값을 알 수 없는 경우와 속도 메시지가 끊긴 경우의 test가 없었다 | `TC-107`, `RT-001`을 더했다 |
| clang-tidy | 기능의 코드에 같은 내용의 분기가 둘 있었다 | 조건을 합쳤다 |
| cppcheck (MISRA 검사) | 변수 이름 `pedal`을 규칙 7.3 위반으로 낸다 | 거짓 경보다. 기록만 했다 (`notes/tool-check.md`) |

## 7. 하지 않은 것

- 감시 자신이 고장 난 경우의 fault injection (단계 2)
- task를 건너뛰거나 늦게 실행하는 경우 (단계 2. 시뮬레이션의 실행 시간은 0이다)
- CAN 메시지의 손상, 되풀이, 지연 (단계 2)
- 실제 MCU에서의 실행 시간과 stack 사용량
