# 하드웨어에 대한 가정과 진단의 목록

예제는 소프트웨어의 예제이고 하드웨어의 설계가 없다. 그래도 소프트웨어의 안전은 하드웨어에 기댄다. 이 문서는 소프트웨어가 하드웨어에 기대는 것을 가정으로 적고, 소프트웨어가 맡는 진단을 목록으로 적는다.

- 등급과 수치는 설명을 위한 가정이다. 규격의 요구사항을 만족하는지 확인한 것이 아니다.
- 여기의 가정은 어느 것도 PC 시뮬레이션으로 보일 수 없다. sim에는 MCU가 없다.
- 실제 프로젝트에서는 이 가정의 근거가 MCU와 부품의 제조사가 주는 문서에 있어야 한다. 이 책은 그런 문서를 확인하지 못했다. 아래의 가정은 [dfa.md](dfa.md)와 [fmea.md](fmea.md)가 "하드웨어에 대한 가정으로 둔다"고 적은 줄에서 거꾸로 뽑은 것이다.

## 1. 가정

[scope.md](scope.md)의 `A-10`, `A-11`과 [technical-safety-concept.md](technical-safety-concept.md)의 `A-19`를 나누어 적은 것이다.

| ID | 가정 | 어느 분석의 줄에서 왔는가 | 깨지면 |
|---|---|---|---|
| `HA-01` | 주 MCU와 따로 동작하는 감시 요소 (외부 watchdog)가 있다. 정해진 때에 옳은 답을 받지 못하면 MCU의 소프트웨어를 거치지 않고 구동 허용 신호를 끊는다. 이 요소는 MCU와 clock을 함께 쓰지 않고, 소프트웨어가 설정을 바꿀 수 없다. 이 요소는 MCU를 reset하지 않는다. 끊은 것은 MCU가 reset되어도 유지되고, VCU의 전원을 껐다 켤 때까지 풀리지 않는다 | [dfa.md](dfa.md) D-4, [fmea.md](fmea.md) FM-13, FM-21 | 감시의 실행을 감시하는 것 (M5)이 뜻을 잃는다. MCU가 멈추면 마지막 출력이 남는다. 끊은 것이 MCU의 reset에 풀리면, 다시 켜진 소프트웨어가 3주기 뒤에 구동을 다시 허용한다 |
| `HA-02` | memory에 오류 검출과 정정이 있다. bit 하나의 오류는 고치고, 둘의 오류는 알아챈다. 고치지 못한 오류에서는 MCU를 reset한다 | [dfa.md](dfa.md) D-2 (memory) | bit의 반전이 조용히 틀린 값이 된다. M7 (뒤집은 사본)을 구현하지 않았으므로 상태 변수의 bit 반전을 막는 것은 이 가정 하나다 |
| `HA-03` | memory 보호 장치가 기능의 영역과 감시의 영역을 나눈다. 기능의 코드는 감시의 data에 쓸 수 없다 | [fmea.md](fmea.md) FM-12, [dfa.md](dfa.md) D-2 (memory) | 기능의 결함이 감시를 틀리게 한다. fault tree의 AND가 값을 잃는다 |
| `HA-04` | task의 실행 시간을 감시한다. 기능이 정해진 시간을 넘으면 멈추게 한다 | [fmea.md](fmea.md) FM-13, [dfa.md](dfa.md) D-2 (processor의 시간) | 기능이 오래 걸려 감시가 늦는다. M5와 `HA-01`이 뒤에서 잡는다 |
| `HA-05` | 전원의 전압을 감시한다. 범위를 벗어나면 MCU를 reset 상태로 잡고, 그동안 구동 허용 신호는 끊겨 있다 (`A-11`) | [dfa.md](dfa.md) D-2 (MCU, clock, 전원) | 전압이 낮은 동안 MCU가 틀린 계산을 내보낸다 |
| `HA-06` | MCU의 clock을 감시한다. 멈추거나 26% 넘게 느려지면 (또는 그만큼 빨라지면) reset한다 | [dfa.md](dfa.md) D-2 | 주기가 틀려진다. 판정의 횟수로 센 시간이 모두 틀려진다. `HA-01`이 따로 된 clock으로 일부를 잡는다: 주기가 1.5배보다 길어지거나 0.5배보다 짧아진 경우다 (10 ms의 주기와 5 - 15 ms의 창). 그보다 작은 어긋남은 이 가정이 맡는다. 허용할 폭은 시간의 예산에서 나왔다: inverter의 검사의 예산 171 ms 가운데 주기로 센 110 ms가 1.26배가 되면 합이 200 ms다 ([technical-safety-concept.md](technical-safety-concept.md) 9.1절). 실제 MCU의 clock 감시가 이 폭을 지키는지는 확인하지 않았다 |
| `HA-07` | ADC가 알려진 기준 전압을 읽어 변환이 맞는지 확인할 수 있다 | [dfa.md](dfa.md) D-1 (ADC와 기준 전압), [fmea.md](fmea.md) FM-02 | 기준 전압이 틀리면 페달의 두 채널이 함께 틀리고, 입력 검사는 알아채지 못한다 |
| `HA-08` | 켤 때 processor, RAM, 프로그램 memory를 시험하고, 실패하면 구동을 허용하지 않는다 | [fmea.md](fmea.md)의 숨은 고장 줄 (FM-14, FM-16) | 하드웨어의 고장이 숨은 채로 달리기 시작한다 |
| `HA-09` | 구동 허용 신호의 선을 되읽는 입력이 있다 | [fmea.md](fmea.md) FM-20, [stpa.md](stpa.md) LS-13 | 끊지 못하는 고장이 쓸 때까지 숨는다 |
| `HA-10` | 비휘발성 memory와 reset의 원인을 알려 주는 register가 있다 | [stpa.md](stpa.md) LS-14 | reset이 고장 상태를 지운다 |
| `HA-11` | 소프트웨어가 첫 주기를 돌 때 센서의 전원과 출력은 이미 안정되어 있다. 켜는 순서를 하드웨어가 지킨다 | [hsi.md](hsi.md) 4절 (묶음 2의 검토에서 나왔다) | 켤 때마다 페달 고장으로 시작한다. 구동을 허용하지 않으므로 `SG-01`에는 안전하고 `SG-02`에는 대가다 |
| `HA-12` | 가속 페달의 입력 회로는 선이 끊기면 0 V 근처로 읽히게 되어 있다 (입력을 접지 쪽으로 당긴다) | [hsi.md](hsi.md) 2절, 5절 | 끊긴 선이 범위 안의 값으로 읽히면 범위 검사가 알아채지 못한다. 두 채널의 견줌만 남는다 |
| `HA-13` | 브레이크 접점의 입력 회로는 선이 끊기면 접점 1 (밟으면 열린다)을 "밟음"으로, 접점 2 (밟으면 닫힌다)를 "놓음"으로 읽는다 | [hsi.md](hsi.md) 5절 | 두 접점이 함께 끊겼을 때 서로 맞게 읽히면 견줌이 알아채지 못한다 |
| `HA-14` | CAN의 송신 함수는 메시지를 넘기고 바로 돌아온다. 송신이 밀려도 주기의 실행을 막지 않는다. 밀린 토크 요구는 새 것으로 덮어쓴다. 묵은 요구가 쌓였다가 늦게 나가지 않는다 | [hsi.md](hsi.md) 3절, 4절 | 출력 단계가 늦어진다. 시간의 예산이 깨진다 |
| `HA-15` | processor의 고장으로 계산이 틀리게 되는 것을 달리는 중에 정해진 시간 안에 알아채고, MCU를 reset하거나 구동 허용 신호를 끊는다 (예: 두 core가 같은 계산을 하고 하드웨어가 결과를 견주는 lockstep, 주기마다 도는 core의 시험) | 묶음 3의 검토 (`reviews/2026-11-23-stage2-part3/`의 F-02), [dfa.md](dfa.md) D-2 (MCU) | 감시의 계산 (허용 토크)이 조용히 틀린다. 외부 watchdog은 이것을 보지 못한다. 답을 만드는 것이 같은 MCU이고, 답은 그 MCU가 계산한 허용 토크와 보낸 토크를 견주어 만들기 때문이다. 기능의 고장과 겹치면 `SG-01`을 어긴다 |

## 2. 누가 하는가

가정마다 하드웨어가 스스로 하는 것과 소프트웨어가 해 주어야 하는 것을 나눈다. 소프트웨어의 몫은 요구사항이 된다.

| 가정 | 하드웨어가 한다 | 소프트웨어가 한다 | 예제에서 |
|---|---|---|---|
| `HA-01` | 답을 기다리고, 틀리거나 늦으면 끊는다 | task가 순서대로 실행되었는지를 확인해 답을 만든다 | 구현했다 (`SWR-20`). watchdog은 sim의 model이다 |
| `HA-02` | 검출과 정정 | 알려 온 오류에 반응한다 | 하지 않는다. sim에 없다 |
| `HA-03` | 접근을 막는다 | 영역을 설정한다. 설정이 맞는지 켤 때 확인한다 | 하지 않는다. 가정으로 둔다 |
| `HA-04` | 시간을 잰다 | 예산을 설정한다 | 하지 않는다. sim에서 실행 시간은 0이다 |
| `HA-05`, `HA-06` | 감시하고 reset한다 | reset의 원인을 읽고 그에 맞게 시작한다 | 하지 않는다 (M8을 구현하지 않았다). reset 뒤에는 정상 상태에서 시작한다 |
| `HA-07` | 기준 전압을 준다 | 주기마다 기준 전압을 읽어 견준다 | 하지 않는다. 가정으로 둔다 |
| `HA-08` | 시험할 수단을 준다 (내장된 시험) | 켤 때 시험을 돌리고 결과를 본다 | 하지 않는다. sim의 소프트웨어는 하드웨어가 고장 나지 않으므로 이 시험은 늘 통과한다 |
| `HA-09` | 선을 되읽는 입력 | 쓴 다음 주기마다 되읽어 견준다 | 구현했다 (`SWR-21`) |
| `HA-10` | 저장하고 원인을 알려 준다 | 고장 상태를 쓰고, 켤 때 읽는다 | 하지 않는다 (M8을 구현하지 않았다) |
| `HA-11` | 켜는 순서를 지킨다 | 없다. 깨지면 페달 고장으로 판정한다 | 가정으로 둔다 |
| `HA-12`, `HA-13` | 끊긴 선이 정해진 쪽으로 읽히게 한다 | 그쪽을 고장으로 (또는 안전한 값으로) 다룬다 | 있다 (페달은 `SWR-02`, 브레이크는 `SWR-15`) |
| `HA-14` | 송신을 queue에 넣는다 | 구동 허용 신호를 CAN보다 먼저 쓴다 | 했다 |
| `HA-15` | 계산을 견주거나 시험하고, 틀리면 reset하거나 끊는다 | lockstep이면 없다. 주기마다 도는 시험이면 시험을 부르고 결과를 본다 | 하지 않는다. sim에 없다 |

## 3. 예제의 소프트웨어가 하는 진단

단계 2가 끝났을 때의 목록이다. "상태"는 지금의 상태다.

| 진단 | 언제 | 찾는 것 | 찾으면 | 상태 |
|---|---|---|---|---|
| 페달 두 채널의 범위와 불일치 | 주기마다 | 센서와 배선의 고장 (한 채널) | 작은 쪽을 쓴다. 3주기 이어지면 고장으로 판정 | 있다 (`SWR-02` - `SWR-04`) |
| 간헐 고장의 판정 | 주기마다 | 가끔 틀리는 채널 (실패가 100주기에 10번을 넘는다) | 고장으로 판정 | 있다 (`SWR-14`) |
| 브레이크 접점 둘의 견줌 | 주기마다 | 스위치와 배선의 고장 | "밟음"으로 두고 고장으로 판정 (어긋난 채 200 ms) | 있다 (`SWR-15`) |
| 받는 메시지의 counter, CRC, timeout | 메시지마다 | 전송의 고장, 보내는 쪽의 멈춤 | 값을 무효로 한다 | 구현했다 (`SWR-18`) |
| 실제 토크의 되읽기 | 주기마다 | inverter가 요구보다 크게 낸다 | 구동 허용을 끊는다 | 구현했다 (`SWR-19`) |
| 실행의 순서와 횟수 | 주기마다 | task가 실행되지 않거나 순서가 틀리다 | 외부 watchdog에 틀린 답이 간다 | 구현했다 (`SWR-20`) |
| 구동 허용 신호의 되읽기 | 켤 때, 끊을 때 | 끊지 못하는 고장 | 구동을 허용하지 않는다 | 구현했다 (`SWR-21`). 주기마다 견준다 |
| 뒤집은 사본의 견줌 | 읽을 때마다 | 고른 변수의 bit 반전 | 구동 허용을 끊는다 | 구현하지 않았다 (M7) |
| 고장 기록의 읽기 | 켤 때 | 지난 운행의 고장 | 그 상태에서 시작한다 | 구현하지 않았다 (M8) |

## 4. 하지 않는 진단

| 진단 | 하지 않는 까닭 | 그래서 못 하는 주장 |
|---|---|---|
| processor, RAM, 프로그램 memory의 시험 (켤 때 `HA-08`, 달리는 중 `HA-15`) | sim에 하드웨어가 없다. 넣어도 늘 통과한다 | 하드웨어의 고장이 숨은 채 달리지 않는다는 주장. 허용 토크의 계산이 달리는 중의 하드웨어 고장으로 틀리지 않는다는 주장 |
| ADC 기준 전압의 확인 | sim의 ADC는 오차가 없다 | 두 채널이 VCU 안의 원인으로 함께 틀리지 않는다는 주장 |
| memory 보호의 설정과 확인 | sim에 memory 보호가 없다 | 기능이 감시를 방해하지 않는다는 주장 |
| 실행 시간의 측정 | sim에서 실행 시간은 0이다 | 감시가 제때 실행된다는 주장. 고장이 없으면 외부 watchdog이 끊지 않는다는 주장 (답의 간격이 흔들리지 않는다) |
| 외부 watchdog이 끊을 수 있는지의 시험 (켤 때 일부러 틀린 답을 주고 되읽기로 끊김을 확인한다) | 예제를 작게 두려고 하지 않았다. 하려면 watchdog에 시험 뒤에 한 번 풀어 주는 방식이 있어야 하고, 그것을 `HA-01`에 적어야 한다 | 끊지 못하는 watchdog이 숨은 채 달리지 않는다는 주장 |
| inverter의 검사 (`SWR-19`)와 실행의 확인 (`SWR-20`)이 고장을 알릴 수 있는지의 시험 | 하지 않았다. 둘은 소프트웨어이고, 켤 때마다 시험할 것은 그것이 기대는 하드웨어다 | 이 두 검사가 기대는 하드웨어 (받는 메시지의 경로, watchdog)의 숨은 고장이 운행마다 드러난다는 주장 |

켤 때 시험하는 safety mechanism의 숨은 고장은 하나뿐이다: 소프트웨어가 구동 허용 신호를 끊을 수 있는가 (`SWR-12`, `SWR-21`). 위의 여섯은 모두 safety case에서 가정으로 남는다.
