# 16장. Testing

## 핵심 질문

언제 "충분히 테스트했다"고 말할 수 있는가?

## test가 답하는 것

test는 "이 입력에서 이렇게 동작했다"를 보인다. "어떤 입력에서도 이렇게 동작한다"는 보이지 못한다. 조합이 너무 많다. 차량 수준의 test가 쓸모 있고 중요하지만, 가능한 운전 조건, 시간 순서, 고장의 조합을 다 해 볼 수는 없다 (Koopman, 2014).

그래서 "충분히"는 양의 문제가 아니다. 세 가지 물음에 답할 수 있는가의 문제다.

1. 요구사항을 모두 test했는가
2. 그 test가 코드를 빠짐없이 실행했는가
3. 그 test는 결함이 있으면 실패하는가

## 1. 요구사항에서 test를 만든다

test는 코드를 보고 만들지 않는다. 요구사항을 보고 만든다. 코드를 보고 만든 test는 코드가 하는 일을 확인할 뿐이고, 해야 하는 일을 확인하지 못한다.

요구사항 하나에서 test를 뽑을 때 보는 것:

- 정상인 경우와 정상이 아닌 경우
- 경계: 한계값, 한계값의 바로 앞과 바로 뒤
- 시간: 몇 번째 주기에 바뀌는가. 그 앞 주기에는 바뀌지 않는가
- 상태: 고장 뒤에 유지되는가. 돌아오지 않아야 할 때 돌아오지 않는가
- 하면 안 되는 것: 고장이 없을 때 대응이 일어나지 않는가

요구사항이 "50을 넘으면"이라면 test는 50과 51을 쓴다. 300과 900만 쓴 test는 한계가 100으로 바뀌어도 통과한다.

test의 기댓값은 요구사항의 숫자로 적는다. 제품 코드의 상수 이름을 가져다 쓰지 않는다. `LIMIT - 1`과 `LIMIT`으로 경계를 test하면, 누가 `LIMIT`을 잘못 바꿔도 test가 같이 따라가서 통과한다.

## 2. structural coverage: 빠진 곳을 찾는다

structural coverage는 test가 코드의 구조를 얼마나 실행했는지를 잰다. test를 만드는 방법이 아니다. 요구사항에서 만든 test를 돌린 뒤에, 실행되지 않은 곳을 찾는 수단이다 (Hayhurst 외, 2001).

실행되지 않은 곳이 나오면 까닭은 셋 가운데 하나다.

- test가 빠졌다. 요구사항은 있는데 그 경우를 test하지 않았다
- 요구사항이 빠졌다. 코드는 있는데 그 동작을 적은 요구사항이 없다
- 쓰이지 않는 코드다

어느 쪽이든 coverage를 채우려고 test를 덧대는 것은 답이 아니다. 까닭을 찾아야 한다.

재는 기준은 촘촘함이 다르다.

| 기준 | 묻는 것 |
|---|---|
| statement coverage | 모든 문장이 한 번은 실행되었는가 |
| decision coverage | 모든 판단이 참과 거짓으로 한 번씩 갔는가 |
| MC/DC | 판단 안의 조건 하나하나가 혼자서 판단의 결과를 바꾼다는 것을 보였는가 |

판단 하나에 조건이 여럿 있으면 차이가 커진다. `if (a || b || c)`는 `a`만 참인 test 하나와 모두 거짓인 test 하나로 문장과 판단을 다 채운다. 그러나 `b`와 `c`는 한 번도 결과를 바꿔 보지 못했다. `b`의 조건이 틀려 있어도 test는 통과한다. MC/DC는 조건이 n개인 판단에 보통 적어도 n+1개의 test를 요구한다 (Hayhurst 외, 2001).

MC/DC에는 조건이 "혼자서 결과를 바꾼다"를 보이는 방식이 둘 있다. unique-cause는 다른 조건을 모두 고정하고 그 조건만 바꾼다. masking은 다른 조건이 결과에 영향을 주지 못한다는 것을 논리로 보인다 (Hayhurst 외, 2001). 도구마다 재는 방식과 세는 단위가 다르다. 그래서 숫자만 옮겨 적지 말고 어느 도구가 무엇을 세었는지를 함께 적는다.

## 3. fault injection: 고장이 났을 때를 test한다

안전 요구사항의 절반은 "고장이 나면"으로 시작한다. 그 test는 고장을 넣어야 할 수 있다.

- 무엇을 넣는가: 안전 분석 (8장)에서 찾은 고장. 떠오르는 대로 넣지 않는다
- 어디에 넣는가: 제품의 코드 밖에서. 제품의 코드에 test용 갈래를 넣으면 test한 것과 싣는 것이 달라진다
- 무엇을 보는가: 알아챘는가, 정한 대응을 했는가, 정한 시간 안에 했는가
- 언제 넣는가: 주기 안의 여러 시점에. 주기가 시작된 직후에 난 고장은 다음 주기까지 기다린다. 가장 나쁜 시간은 그때 나온다

알아채지 못하는 고장도 넣어 본다. "이 감시는 이것을 잡지 못한다"를 test로 남겨 두면 한계가 문서와 코드에 함께 적힌다.

## 4. test를 test한다

coverage 100%는 test가 코드를 지나갔다는 뜻이다. 지나가면서 옳은지를 확인했다는 뜻은 아니다. 확인하는 문장이 하나도 없는 test도 coverage를 채운다.

이것을 보는 방법은 코드에 결함을 일부러 넣는 것이다. 한계값을 바꾸고, 조건 하나를 빼고, 부등호를 뒤집는다. 그때 test가 실패하지 않으면 그 test는 그 결함을 잡지 못한다.

같은 생각을 한 단계 위에서도 쓴다. fault를 넣고 "safety goal이 지켜졌다"를 확인했다면, 안전 장치를 빼고 같은 fault를 넣어 본다. 그때 safety goal이 깨지지 않으면 그 test는 안전 장치를 시험한 것이 아니다. 넣은 fault가 너무 작았거나 판정이 너무 느슨한 것이다.

넣는 결함을 누가 고르는지도 중요하다. test를 쓴 사람이 고른 결함은 그 사람이 이미 생각한 것이다.

## 어디에서 돌리는가

| 환경 | 돌리는 것 | 보이는 것 | 못 보이는 것 |
|---|---|---|---|
| PC, 소프트웨어만 | 제품의 source를 PC용으로 빌드 | 논리, 요구사항과의 일치 | target의 compiler, 실행 시간, 메모리 |
| target의 processor | 제품과 같은 compiler로 빌드한 것 | compiler와 processor의 차이 | 주변 하드웨어, 실제 신호 |
| 실제 제어기와 모의 환경 | 실릴 그대로의 소프트웨어와 하드웨어 | 실행 시간, 입출력, 통신 | 실제 차량의 동작 |
| 차량 | 전부 | 차량 수준의 동작 | 드문 조건과 고장의 조합 |

이 책의 예제는 첫째 줄에 있다. PC에서 통과한 test가 말해 주는 것은 "이 source의 논리가 요구사항과 맞는다"까지다. test한 것이 실릴 그 빌드인가는 따로 물어야 한다.

## 관통 예제에 적용

결과는 `example/drive-torque/docs/test-report.md`에 있다. `make check`와 `make mutation`의 결과를 옮겨 적은 문서다. 다시 돌린 결과는 `build/reports/` 아래에 생긴다.

| 물음 | 예제가 한 것 | 결과 |
|---|---|---|
| 요구사항을 모두 test했는가 | 구현한 요구사항 20개마다 test case를 잇고, 스크립트가 빠진 것을 찾는다 | test case 50개. 빠진 것 없음 |
| 코드를 빠짐없이 실행했는가 | GCC로 statement, branch, MC/DC를 잰다 | 제품 코드 10개 파일 모두 100% |
| test는 결함을 잡는가 | 제품 코드에 결함 164개를 하나씩 넣는다 | 164개 모두 test가 실패했다 |
| test는 감시를 시험하는가 | 감시를 빼고 같은 fault를 넣는다 | safety goal을 어겼다 (가속의 차이 1.81 m/s^2). 감시가 있으면 0.08이다 |
| 고장이 났을 때는 | fault 22가지를 넣는다. 시점을 주기 안에서 0-9 ms로 바꾼다 | 가장 나쁜 시간 29 ms, 49 ms. 다섯은 알아채지 못한다는 것을 기록했다 |

만드는 동안 이 수단들이 실제로 찾은 것이 더 쓸모 있는 이야기다.

- coverage가 빠진 test를 찾았다. 처음에 입력을 읽는 코드의 MC/DC는 42%였다. 기어 값이 알 수 없는 값일 때의 test가 없었다. 요구사항에 따른 test를 다 썼다고 생각한 뒤였다.
- 증명이 test가 놓친 결함을 찾았다. 전압을 페달 위치로 바꾸는 함수가 뺄셈을 먼저 하고 있었다. 하드웨어가 범위 밖의 값을 주면 overflow가 난다. 그때 test는 모두 통과하고 있었다. test는 넣어 본 값만 본다 (15장).
- 예제를 만들기 전에 도구를 확인하려고 만든 시제품에서, 같은 test 묶음이 줄은 100% 덮고 MC/DC는 43%만 덮었다. 조건이 다섯 개인 판단문에 test가 둘뿐이었다. 같은 묶음을 다른 compiler로 재면 20%가 나왔다. 세는 단위가 달랐다. 기록은 `notes/tool-check.md`에 있다.
- MC/DC 100%인 test가 결함을 놓쳤다. 처음의 변이 검사는 10개를 넣어 10개를 잡았다. 검토자가 21개를 더 넣자 4개를 놓쳤다. 허용 오차를 0으로 바꿔도, 페달 놓음 구간을 30에서 20으로 바꿔도 test는 통과했다. test의 기댓값이 제품의 상수 이름을 쓰고 있었기 때문이다. 이 장이 가르치는 잘못을 예제의 test가 하고 있었다.
- 차량 수준의 판정이 감시 없이도 통과하고 있었다. 처음 넣은 fault (30 Nm)는 감시를 빼도 가속의 차이가 0.54 m/s^2여서 safety goal의 한계 (1.0)에 닿지 않았다. fault를 100 Nm로 키우고 감시를 뺀 대조를 더했다.
- 변이 검사 도구가 틀리게 세고 있었다. "잡았다"고 센 변이 하나는 실은 compile되지 않는 것이었다. 도구도 검사해야 한다 (17장).
- 가장 큰 결함은 어느 도구도 찾지 못했다. 감시의 허용 토크가 정상 동작보다 훨씬 큰 운전 상태가 있었고, 거기에서 기능이 틀리면 감시를 지나 safety goal을 어겼다 (7장). 요구사항이 빠져 있었으므로 그것을 확인하는 test도 없었다. coverage 100%, 증명 4개, 변이 검사가 모두 통과한 뒤에 검토에서 찾았다.
- 그 요구사항을 더하고 test (`TC-007`)를 쓴 뒤에도 같은 결함이 한 곳 남아 있었다. test는 페달과 기어와 브레이크의 격자를 돌았지만, 브레이크를 밟았다 놓는 순서는 돌지 않았다. 기능에는 그 순서에서만 생기는 상태가 있었다. 상태가 있는 코드의 test는 입력의 값만이 아니라 입력의 순서를 덮어야 한다. 격자가 촘촘하다는 것은 순서를 덮었다는 뜻이 아니다.

요구사항에 따른 test 하나는 이렇게 생겼다.

```c
/* TC-009: SWR-08 깎인 주기가 5번 이어지면 기능의 고장으로 고정한다 */
static void tc_009(void)
{
    output_stage_t st;

    output_stage_init(&st);
    /* 4번 깎이고 한 번 정상이면 다시 센다 */
    for (int i = 0; i < 4; i++) {
        CHECK_EQ(output_stage_step(&st, 2000, 1000, GEAR_D), 1000);
    }
    CHECK(!st.latched);
    CHECK_EQ(output_stage_step(&st, 900, 1000, GEAR_D), 900);
    for (int i = 0; i < 4; i++) {
        (void)output_stage_step(&st, 2000, 1000, GEAR_D);
    }
    CHECK(!st.latched);
    /* 5번째로 이어서 깎인 주기에 고정한다 */
    (void)output_stage_step(&st, 2000, 1000, GEAR_D);
    CHECK(st.latched);
    CHECK_EQ(st.clamp_count, 9);
}
```

4번째까지는 고정되지 않는다는 것, 한 번 정상이면 다시 센다는 것, 5번째에 고정된다는 것을 따로 확인한다. 요구사항의 문장 하나하나에 확인이 하나씩 있다.

## sim이 보이는 것과 못 보이는 것

| 보이는 것 | 못 보이는 것 |
|---|---|
| source의 논리가 요구사항과 맞는다 | target의 compiler가 만든 기계어가 같게 동작한다는 것 |
| 고장을 넣은 때부터 출력이 바뀔 때까지의 주기 수 | 실제 실행 시간과 통신 지연 |
| 가정한 plant model에서 차량의 가속 | 실제 inverter, 모터, 차량의 응답 |
| `-O0`으로 빌드한 source 수준의 coverage | 실릴 빌드의 coverage |

## 규격에서의 위치

- ISO 26262-6 (Product development at the software level)
- IEC 61508-3 (Software requirements)
- 항공: DO-178B와 그 뒤를 이은 DO-178C. 등급에 따라 요구하는 coverage가 다르다 (3장). 이 장의 MC/DC 설명은 이 분야의 공개 지침서를 따랐다

등급에 따라 어떤 test 방법과 coverage를 요구하는지는 규격의 표에 있다. 이 책은 그 표를 싣지 않는다.

## 흔한 오해

- "coverage 100%면 충분히 test한 것이다." coverage는 지나갔는지만 본다. 확인했는지는 보지 않는다. 빠진 요구사항도 보지 못한다. 예제에서 MC/DC 100%인 test가 상수의 변이 넷을 놓쳤고, 빠진 요구사항 하나는 검토에서야 나왔다.
- "coverage가 모자라면 test를 더 넣으면 된다." 먼저 왜 실행되지 않았는지를 찾는다. 요구사항이 빠진 것일 수 있다.
- "MC/DC는 모든 조합을 test하는 것이다." 조건이 n개면 조합은 2의 n제곱 개다. MC/DC는 n+1개쯤으로 조건마다의 영향을 본다.
- "PC에서 통과했으니 된 것이다." PC의 결과는 논리에 관한 것이다.
- "차를 오래 몰아 봤으니 안전하다." 드문 고장의 조합은 주행 시험에서 나오지 않는다.

## 확인 문제

1. `if ((!valid && cmd > 0) || (brake && cmd > limit_b) || (cmd > limit))`에 statement coverage 100%를 주는 가장 적은 test는 몇 개인가? MC/DC에는 적어도 몇 개가 필요한가?
2. 예제에서 fault를 주기가 시작된 직후 (1 ms 뒤)에 넣었을 때와 직전 (9 ms 뒤)에 넣었을 때, 판정까지의 시간은 각각 얼마인가?
3. 확인하는 문장이 없는 test가 coverage를 채우는 것을 어떻게 찾아낼 수 있는가?
4. "알아채지 못한다"를 통과 조건으로 하는 test를 남겨 두는 까닭은 무엇인가?
5. fault injection test가 감시가 없어도 통과한다면 무엇을 의심해야 하는가? 두 가지를 들어 보라.
