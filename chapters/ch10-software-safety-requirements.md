# 10장. Software safety requirements

## 핵심 질문

검증할 수 있는 안전 요구사항은 어떻게 쓰는가?

## 요구사항이 틀리면 나머지가 다 틀린다

코드는 요구사항대로 만들고, test는 요구사항대로 동작하는지 본다. 그래서 요구사항이 틀리거나 빠지면 코드와 test가 완벽해도 시스템은 위험하다. 2장에서 본 것처럼 부품이 모두 명세대로 동작해도 사고는 난다.

software safety requirement는 7장의 계단에서 가장 아래다. 여기까지 내려오면 요구사항은 소프트웨어의 한 부분이 정확히 무엇을 하는지를 말해야 한다. test를 짤 수 있을 만큼 구체적이어야 한다.

## 좋은 요구사항

NASA의 소프트웨어 안전 지침서는 요구사항이 갖출 것을 이렇게 든다 (NASA, 2004).

| 속성 | 뜻 | 어기면 |
|---|---|---|
| 모호하지 않다 | 읽는 사람마다 같은 뜻으로 읽는다 | 만든 것과 원한 것이 다르다 |
| 빠짐없다 | 필요한 동작이 모두 적혀 있다 | 적히지 않은 경우의 동작을 구현자가 정한다 |
| 서로 어긋나지 않는다 | 두 요구사항이 부딪치지 않는다 | 어느 쪽을 따라도 틀린다 |
| 추적할 수 있다 | 어디에서 나왔는지 적혀 있다 | 왜 있는지 모르는 요구사항이 남는다 |
| 검증할 수 있다 | test, 분석, 검토로 만족했는지 볼 수 있다 | 만족했는지 아무도 모른다 |

안전 요구사항에서 특히 지킬 것을 더한다.

- 하나의 요구사항은 한 가지만 말한다. "검사하고, 실패하면 끊고, 경고한다"는 세 개다. 나눠야 test와 하나씩 짝지을 수 있다.
- 값을 적는다. "빨리"가 아니라 "3번째 주기에", "크면"이 아니라 "50을 넘으면". 경계에 있는 값 (50일 때)이 어느 쪽인지도 정한다.
- 해결 방법이 아니라 밖에서 볼 수 있는 동작을 적는다. "counter 변수를 올린다"가 아니라 "깎은 주기가 5번 이어지면 고정한다".

## 빠뜨리기 쉬운 것

요구사항은 정상일 때의 동작부터 쓰게 된다. 사고는 그 밖에서 난다. 아래를 하나씩 물어본다.

| 물음 | 예제에서의 답 |
|---|---|
| 입력이 범위를 벗어나면 | 전압이 센서의 범위 밖이면 그 주기의 검사는 실패다 (`SWR-02`) |
| 입력이 서로 맞지 않으면 | 두 채널의 차이가 50을 넘으면 실패다 (`SWR-02`) |
| 이상이 얼마나 이어져야 고장인가 | 3주기 (`SWR-03`), 5주기 (`SWR-08`) |
| 판정 전에는 무엇을 내보내는가 | 두 채널 가운데 작은 값을 쓴다 (`SWR-04`) |
| 고장 뒤에는 어떤 상태인가 | 토크 0 (`SWR-09`), 구동 허용 신호 차단 (`SWR-10`) |
| 고장 상태에서 언제 돌아오는가 | 돌아오지 않는다. 다시 켤 때까지 유지한다 (`SWR-03`, `SWR-09`) |
| 켠 직후에는 | 검사를 3주기 통과하기 전에는 페달 값을 0으로 본다 (`SWR-04`) |
| 얼마 안에 | 7장의 시간 예산에서 온다 (`TSR-02`, `TSR-05`) |
| 하면 안 되는 것은 | 고장이 없으면 구동 허용 신호를 끊지 않는다 (`SWR-10`) |

마지막 줄을 보자. 안전 요구사항은 "고장이면 끊는다"만 쓰기 쉽다. "고장이 아니면 끊지 않는다"를 함께 써야 한다. 잘못 끊는 것도 hazard이기 때문이다 (6장).

NASA의 지침서는 시간에 관한 요구사항을 따로 다룬다. 고장이 난 때부터 시스템이 위험한 상태에 이를 때까지의 시간을 알아야 자동으로 대응할지 사람에게 맡길지를 정할 수 있다고 한다 (NASA, 2004).

## 추적

요구사항에는 ID를 붙이고 위와 아래를 잇는다.

- 위로: 이 요구사항은 어느 요구사항에서 나왔는가. 위가 없는 요구사항은 왜 있는지 모르는 것이다.
- 아래로: 이 요구사항은 어느 코드가 구현하고 어느 test가 확인하는가. 아래가 없는 요구사항은 구현되지 않았거나 확인되지 않은 것이다.

추적은 손으로 하면 금세 낡는다. 예제는 요구사항을 텍스트 파일 하나에 두고, 코드와 test의 주석에 ID를 적고, 스크립트가 빠진 것을 찾는다. 도구가 무엇이든 원리는 같다: 요구사항, 코드, test가 같은 ID로 묶이고, 묶임이 깨지면 빌드가 실패한다.

## 안전 요구사항이 아닌 것과 함께 있을 때

제어기의 요구사항 대부분은 안전 요구사항이 아니다. 둘은 표시로 나눈다. 그래야 변경이 생겼을 때 안전에 닿는 변경인지 알 수 있다 (18장).

예제에서 토크 요구를 만드는 기능은 `SG-01`에 대해서 안전 요구사항을 받지 않는다. 그래도 기능의 요구사항 하나가 안전 쪽에 걸린다: "정상인 기능의 토크 요구는 허용 토크를 넘지 않는다." 이것이 깨지면 감시가 정상인 기능을 고장으로 판정해 구동을 끊는다. 예제는 이것을 허용 토크의 요구사항 (`SWR-06`)에 적고 test로 확인한다.

## 관통 예제에 적용

요구사항의 원본은 `example/drive-torque/docs/requirements.yaml`이다. `SG-01` 아래에 functional safety requirement 5개, technical safety requirement 7개, software safety requirement 11개가 있다.

요구사항 하나는 이렇게 생겼다.

```yaml
  - id: SWR-03
    alloc: "입력 검사"
    text: "검사에 실패한 주기가 3번 이어지면 페달 고장으로 고정한다. 한 주기라도 통과하면 다시 센다."
    parents: [TSR-02]
    verified_by: [TC-003, TC-102]
    proved_by: [prove_pedal_check]
```

`tools/trace.py`는 다음을 검사한다. 하나라도 어긋나면 `make check`가 실패한다.

- 모든 요구사항이 위 단계의 요구사항에 이어진다
- 모든 software safety requirement의 ID가 코드에 있다
- 모든 software safety requirement에 test case가 있고, 그 test case가 test 코드에 있다
- test 코드의 test case는 모두 어느 요구사항에 이어진다

이 요구사항에는 알려진 빈틈이 있다. 실패와 통과가 번갈아 나오는 간헐 고장은 3번 이어지지 못해 판정되지 않는다. 요구사항을 이렇게 쓰는 순간 그 동작이 정해진 것이다. test (`TC-003`)는 이 동작을 그대로 확인한다. 요구사항의 빈틈은 test가 찾아 주지 않는다. 이 규칙은 검토에서도 의견이 갈렸다. 12장에서 다시 본다.

## 규격에서의 위치

- ISO 26262-6 (Product development at the software level)
- ISO 26262-8 (Supporting processes)
- IEC 61508-3 (Software requirements)

규격이 요구사항에 요구하는 속성의 목록은 이 책에 옮기지 않았다. 위의 표는 공개된 NASA 지침서의 것이다.

## 흔한 오해

- "요구사항은 자세할수록 좋다." 구현을 적은 요구사항은 코드를 두 번 쓴 것이다. 밖에서 볼 수 있는 동작을 적는다.
- "test가 다 통과했으니 요구사항은 옳다." test는 코드가 요구사항과 맞는지를 본다. 요구사항이 옳은지는 보지 못한다.
- "추적표가 있으면 추적이 된 것이다." 표는 낡는다. 기계가 검사하지 않는 추적은 믿기 어렵다.
- "안전 요구사항은 고장일 때의 동작만 쓴다." 고장이 아닐 때 하지 말아야 할 것도 쓴다.

## 확인 문제

1. "페달 신호에 이상이 있으면 빠르게 토크를 줄인다"를 검증할 수 있는 요구사항으로 고쳐 써 보라. 몇 개로 나뉘는가?
2. `SWR-02`에서 두 채널의 차이가 정확히 50이면 검사는 통과인가 실패인가? 그것을 확인하는 test는 값을 몇 개 써야 하는가?
3. 예제의 요구사항에 "고장 상태에서 돌아오는 조건"을 더한다면 어떤 요구사항이 새로 필요한가? 무엇을 잘못 쓰면 위험해지는가?
4. 추적 스크립트가 찾지 못하는 추적의 오류를 하나 들어 보라.
