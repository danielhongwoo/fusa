# 12장. Safety mechanism 구현

## 핵심 질문

고장을 제때 감지하고 반응하는 구체적 수단은 무엇인가?

## safety mechanism이 하는 일

2장의 사슬에서 safety mechanism은 error가 failure로 가는 길을 끊는다. 하는 일은 셋이다: 알아챈다, 판정한다, 대응한다. 셋 모두에 시간이 걸리고, 그 합이 7장의 시간 예산 안에 들어야 한다.

## 알아채는 수단

임베디드 엔지니어에게 낯익은 기법이 대부분이다. 달라지는 것은 그 기법을 어느 고장을 잡으려고, 어떤 근거로 쓰는가다.

| 무엇을 보는가 | 수단 | 잡는 것 | 못 잡는 것 |
|---|---|---|---|
| 입력 값 하나 | 범위 검사 | 단선, 단락 | 범위 안에서 틀린 값 |
| 입력 값 둘 | 서로 견주기 | 한쪽만 틀린 값 | 둘이 함께 틀린 값 |
| 입력과 다른 신호 | 타당성 검사 (예: 페달과 브레이크). 예제에는 없다 | 물리적으로 말이 안 되는 조합 | 말이 되는 틀린 값 |
| 계산의 결과 | 상한을 따로 계산해 견주기 | 범위를 넘는 결과 | 범위 안에서 틀린 결과. 그래서 범위와 정상 동작 사이의 틈이 작아야 한다 |
| 내보낸 값과 돌아온 값 | actuator가 알려 주는 실제 값과 견주기. 예제에는 없다 | actuator가 요구와 다르게 동작함 | actuator의 보고가 틀린 경우 |
| 프로그램의 실행 | watchdog, 실행 순서와 주기의 감시 | 멈춤, 늦음, 순서가 틀림 | 제때 실행되지만 틀린 계산 |
| 받은 메시지 | CRC, counter, ID, timeout | 손상, 유실, 되풀이, 뒤바뀜 | 보내는 쪽이 처음부터 틀린 값 |
| MCU 자체 | 다른 processor가 문제를 내고 답을 검사 | MCU의 연산 고장 | 문제가 덮지 않는 고장 |

표의 마지막 열이 중요하다. 수단마다 잡지 못하는 것이 있고, 그것을 다른 수단이나 가정이 덮어야 한다.

실행의 감시. AUTOSAR의 문서는 실행의 감시를 셋으로 나눈다 (AUTOSAR, 2025).

- 주기적으로 실행되는가 (alive supervision)
- 두 지점 사이의 시간이 정한 범위 안인가 (deadline supervision)
- 정한 순서로 지나가는가 (logical supervision)

loop의 끝에서 watchdog을 두드리는 코드는 첫째만 본다. 그것도 "어딘가는 돌고 있다"만 보인다.

메시지의 보호. 안전에 관련된 값을 보낼 때는 보내는 쪽이 검사 정보를 붙이고 받는 쪽이 검사한다. AUTOSAR의 문서는 통신의 고장과 그것을 잡는 수단을 이렇게 짝짓는다 (AUTOSAR, 2025).

| 통신의 고장 | 잡는 수단 |
|---|---|
| 값이 손상됨 | CRC |
| 같은 메시지가 되풀이됨, 유실됨, 늦음, 순서가 바뀜 | counter |
| 다른 메시지가 끼어듦 | data ID |
| 다른 메시지가 그 메시지로 둔갑함 | data ID와 CRC |
| 채널이 막혀 오지 않음 | counter와 timeout |

알아챈 뒤에 무엇을 할지는 받는 쪽의 응용이 정한다. 보호 장치는 알려 줄 뿐이다.

MCU의 감시. 미국 정부의 보고서는 제어기 하나가 다른 제어기에 미리 답이 정해진 문제를 주기적으로 내고, 정한 시간 안에 맞는 답이 오는지로 건전성을 확인하는 기법을 든다. 등급이 높은 요구사항에 흔히 쓰는 중복 기법이라고 한다 (Becker 외, 2020).

## 판정: 몇 번이면 고장인가

한 번 이상했다고 바로 고장으로 보면 잡음에 멈춘다. 그래서 이상이 이어지는지를 센다 (debounce). 세는 규칙에는 두 가지 흔한 꼴이 있다.

| 규칙 | 세는 법 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| 이어지는 횟수 | 실패하면 올리고, 한 번이라도 통과하면 0으로 되돌린다 | 가장 나쁜 판정 시간이 분명하다 | 실패와 통과가 번갈아 나오는 간헐 고장을 끝내 판정하지 못한다 |
| 올리고 내리기 | 실패하면 올리고, 통과하면 내린다 | 실패가 더 잦은 간헐 고장을 판정한다 | 설명과 검증이 조금 더 복잡하다 |

어느 쪽이든 판정하기 전의 주기에 무엇을 내보낼지를 함께 정해야 한다. 판정을 기다리는 동안 틀린 값이 나가면 debounce만큼 hazard에 다가간다.

고르는 기준은 둘이다.

- 가장 나쁜 판정 시간이 시간 예산 안에 드는가. 이어지는 횟수는 이것을 계산하기 쉽다.
- 그 신호에 간헐 고장이 나는가. 접촉 불량이 있을 수 있는 배선이나 connector를 지나는 신호라면 이어지는 횟수만으로는 고장이 숨는다.

## 대응

대응은 safe state로 가는 일이다. 정할 것은 넷이다.

- 무엇을 하는가: 값을 제한한다, 0으로 한다, 출력을 끊는다
- 누가 하는가: 고장 난 것이 스스로 멈추기를 기대하지 않는다
- 유지하는가: 고장이 사라지면 돌아오는가, 다시 켤 때까지 유지하는가
- 알리는가: 운전자에게 알리고, 정비를 위해 기록한다

보고서의 요구사항에도 대응마다 경고와 고장 기록이 따라붙는다 (Becker 외, 2020).

## 감시는 누가 감시하는가

safety mechanism도 고장 난다. 그리고 평소에는 할 일이 없어서 고장이 드러나지 않는다. 필요한 날 처음 쓰이고, 그날 안 된다. 이것을 막는 방법은 감시를 시험하는 것이다. 보고서는 켤 때의 자가 시험 (CPU, 비휘발성 memory의 checksum)과 주기적인 검사를 요구사항으로 든다 (Becker 외, 2020).

## 관통 예제에 적용

예제가 단계 1에서 구현한 mechanism은 둘이다. 코드는 `example/drive-torque/src/`에 있다.

1. 페달의 입력 검사 (`src/input/pedal_check.c`): 범위 검사와 두 채널 견주기

```c
    /* SWR-02: 채널마다 범위를 보고, 두 채널을 서로 견준다 */
    bool bad = out_of_range(in->apps1_mv, APPS1_LOW_MV, APPS1_HIGH_MV)
               || out_of_range(in->apps2_mv, APPS2_LOW_MV, APPS2_HIGH_MV)
               || (diff > PEDAL_MISMATCH_MAX);
```

판정 전에도 두 채널 가운데 작은 값을 쓴다. 한 채널이 높은 값에 고착되어도 판정을 기다리는 동안 토크가 따라 올라가지 않는다.

2. 토크의 감시와 출력 단계 (`src/monitor/monitor.c`): 상한을 따로 계산해 깎고, 이어지면 차단한다

```c
torque_t output_stage_step(output_stage_t *st, torque_t torque_req, torque_t allowed, gear_t gear)
{
    torque_t out = output_clamp(torque_req, allowed, gear);

    /* SWR-08: 토크 요구가 허용 범위를 벗어난 주기가 이어지면 기능의 고장으로 고정한다 */
    if (out != torque_req) {
        st->clamp_count++;
        if (st->excess_cycles < EXCESS_LATCH_CYCLES) {
            st->excess_cycles++;
        }
        if (st->excess_cycles >= EXCESS_LATCH_CYCLES) {
            st->latched = true;
        }
    } else {
        st->excess_cycles = 0u;
    }

    /* SWR-09: 고정된 뒤에는 토크 0을 보낸다 */
    if (st->latched) {
        return 0;
    }
    return out;
}
```

fault를 넣어 본 결과다 (`docs/test-report.md`).

| fault | 결과 | 잰 시간 |
|---|---|---|
| 페달 채널 1이 높은 값에 고착 | 페달 고장으로 판정, 토크 0, 경고. 판정 전에도 넘는 토크는 없었다 | 토크 요구 0까지 29 ms |
| 기능이 100 Nm 더 큰 토크를 요구 | 넘는 토크는 한 주기도 나가지 않았다. 고정, 차단, 경고 | 차단까지 49 ms |
| 같은 fault, 감시를 뺌 (대조) | 가속의 차이가 1.81 m/s^2로 `SG-01`을 어겼다 | - |
| 후진 중에 기능이 최대 토크를 요구 | 후진의 허용 토크까지만 나갔다. 고정, 차단 | 차단까지 50 ms 안 |
| 두 페달 채널이 함께 올라감 | 알아채지 못했다 | - |
| 기능이 토크를 절반만 냄 | 알아채지 못했다 | - |

"알아채지 못했다"는 두 줄은 실패가 아니다. 이 mechanism이 잡지 못하는 것을 test로 적어 둔 것이다. 앞의 표에서 "못 잡는 것" 열에 해당한다.

대조의 줄도 눈여겨본다. fault를 넣고 "safety goal이 지켜졌다"를 확인했다면, 감시를 빼고 같은 fault를 넣었을 때 safety goal이 깨지는지도 확인해야 한다. 깨지지 않는다면 그 test는 감시를 시험한 것이 아니다. 예제의 처음 test가 그랬다. 넣은 fault가 작아서 감시가 없어도 통과했다.

예제의 세는 규칙은 이어지는 횟수다. 간헐 고장을 판정하지 못한다는 한계가 있고, 요구사항과 test에 그대로 적혀 있다. 이 규칙은 검토에서 의견이 갈렸다. 한쪽은 가장 나쁜 시간이 분명한 것을, 다른 쪽은 간헐 고장을 놓치지 않는 것을 더 무겁게 보았다. 단계 2에서 다시 정한다.

예제의 고장 상태는 RAM의 변수다. 요구사항은 "다시 켤 때까지 유지한다"고 적었지만, 주행 중에 reset이 나면 초기화가 그 변수를 지우고 세 주기 뒤에 토크를 다시 낸다. 고장 상태를 reset 너머로 지키려면 비휘발성 memory에 적거나 reset의 원인을 봐야 한다. 단계 2에서 다룬다.

단계 1에서 하지 않은 것: 켤 때의 자가 시험, 실행의 감시, 메시지의 보호, 브레이크와 기어 신호의 검사, inverter가 알려 주는 실제 토크와의 비교, 감시 자신이 고장 난 경우의 fault injection.

## sim이 보이는 것과 못 보이는 것

| 보이는 것 | 못 보이는 것 |
|---|---|
| 넣은 fault를 정한 주기 안에 알아챈다 | 넣지 않은 fault에 대한 동작 |
| 판정 전과 후에 넘는 토크 요구가 나가지 않는다 (소프트웨어의 논리) | 감시가 실행되지 않는 경우 |
| 판정한 주기에 출력이 바뀐다 | 실제 실행 시간, 통신 지연 |
| | 메모리가 망가져 counter나 고정 표시가 바뀌는 경우 |
| | watchdog과 reset의 동작. 예제의 고장 상태는 reset이 지운다 |
| | 두 ADC 채널을 읽는 시각의 차이, 잡음. 시뮬레이션의 두 채널은 같은 순간의 오차 없는 값이다 |
| | 간헐 고장이 차량에서 어떻게 보이는가 |

## 규격에서의 위치

- ISO 26262-6 (Product development at the software level)
- IEC 61508-3 (Software requirements)
- AUTOSAR의 공개 문서: 실행의 감시와 통신의 보호를 구현한 모듈의 설명

## 흔한 오해

- "watchdog이 있으니 안전하다." watchdog은 멈춘 것을 잡는다. 제때 돌면서 틀린 값을 내는 것은 잡지 못한다.
- "CRC가 맞으면 값이 옳다." CRC는 전송 중의 손상을 잡는다. 보내는 쪽이 틀린 값을 보내면 CRC는 맞는다.
- "센서를 둘 달면 된다." 둘이 맞으면 믿는 검사는 둘이 함께 틀리는 것을 잡지 못한다. 전원, 접지, 기계적인 부분을 함께 쓰면 함께 틀린다.
- "감시는 한 번 만들면 끝이다." 감시의 고장은 숨는다. 시험하지 않으면 필요한 날에야 안다.

## 확인 문제

1. 예제에서 판정 전의 주기에 "큰 값"이 아니라 "작은 값"을 쓰는 까닭은 무엇인가? 이 선택이 나쁘게 작용하는 hazard는 무엇인가?
2. 실패 2주기, 통과 1주기가 되풀이되는 입력을 두 가지 세는 규칙에 각각 넣어 보라. 3에 닿는가?
3. 토크 요구 메시지에 counter가 없으면 어떤 고장을 놓치는가? 예제의 가정 가운데 어느 것이 그 빈틈을 일부 덮는가?
4. 켤 때 "출력 단계가 넘는 토크를 깎는다"를 시험하려면 무엇이 필요한가? 시험 자체가 위험해지지 않으려면 무엇을 지켜야 하는가?
