# 검토 기록: 단계 2의 묶음 4 (15 - 17장과 예제의 검사 도구)

## 대상

- 원고: 15장 (verification 전략)과 17장 (도구와 기존 소프트웨어)의 새 초고, 16장 (testing)의 깊은 수정, 용어집에 더한 스물아홉 항목
- 예제의 도구: `Makefile`의 검사 단계, `tools/coverage.sh`, `tools/variants.sh`, `tools/mutation_check.py`, 증명의 harness, 새로 만든 `tools/step_check.py`
- 예제의 문서: 도구 분류표 (`docs/tools.md`), test 보고서

## 참가자

| 역할 | 모델 | 맡은 일 |
|---|---|---|
| FuSa 전문가 | opus | 안전을 잘못 가르치는가, 근거 문서와의 대조, 결론이 근거보다 넓은가 |
| 임베디드 소프트웨어 엔지니어 | sonnet | 도구와 단계를 실제로 돌려 문서의 말과 견주기, 결함을 넣어 단계가 실패하는지 보기, 변이를 더 넣어 보기 |
| 진행 (Claude 주 세션) | - | 초고의 대조, 구현, 반영, 결정 |

두 검토자는 저장소를 고치지 않고 복사본에서 돌렸다. 1차에서는 서로의 의견을 보지 않았다. 세 장의 초고는 opus 에이전트 셋이 썼고, 진행자가 전부 읽고 받은 문서의 쪽과 웹 출처의 핵심 주장을 직접 대조했다. 사람의 검토는 받지 않았다.

## 결과

판정: 통과. 합의되지 않은 것은 없다. 3차의 반영 (문장 둘과 도구 하나)은 검토자가 다시 보지 않았다.

### 반드시 고칠 것으로 나온 지적 (둘)

| 지적 | 찾은 쪽 | 무엇이 틀렸었는가 |
|---|---|---|
| F-01 | FuSa | 16장이 "충분히 test했다"를 세 물음 (요구사항, 구조, 결함을 잡는가)에 답한 것으로 정의했다. 그 셋은 모두 host의 실행 파일에 대한 것이었고, test가 내보내는 것 (target의 build와 하드웨어)에 대해 말하는가라는 물음이 빠져 있었다. 예제는 그 물음에 "아니다"라고 답해야 하는데, 초고의 정의로는 예제가 충분히 test한 것이 되었다 |
| E-01 | 임베디드 | coverage 단계가 100%에 못 미친다고 찍고도 통과했다. 요약 도구의 출력을 다른 명령으로 넘기는 줄에서 종료 상태가 사라졌다. 16장은 "100%가 아니면 `make check`가 실패한다"고 적고 있었는데, 그 문장은 진행자가 F-01을 고치면서 넣은 것이었고 사실이 아니었다 |

### 되풀이된 것

검사 단계가 실패를 덮는 일이 세 번 나왔고 (정적 분석, coverage, 도구가 없을 때), 그것을 막으려고 만든 확인 (`make step-check`)에도 같은 종류의 틈이 있었다 (실패한 까닭을 보지 않았다). 넷 모두 만든 쪽이 아닌 눈이 찾았다. 도구에 관한 일을 적은 표 (`docs/tools.md` 3절)의 열넷 가운데 만든 쪽이 스스로 찾은 것은 넷이다.

반영하면서 틀린 말이 새로 들어간 일이 두 번 있었다. 16장의 "100%가 아니면 실패한다" (E-01)와, 검토자의 풀이를 출처의 말로 옮겨 적은 17장의 proven in use 문장 (F-12)이다. 둘 다 다음 회의 검토에서 나왔다.

### 저자가 정할 것으로 올라온 것

`PLAN.md` 12절의 25 - 27번에 기본값과 함께 적었다: 16장의 넷째 물음, 도구가 없을 때 `make check`가 실패하게 한 것, Koopman 인용을 뺀 것.

### 하지 못한 것

- 사람의 검토
- 깨끗한 환경 (container)에서 `make check`를 돌리는 것. 지금의 확인은 모두 한 컴퓨터에서 한 것이다
- target의 compiler와 하드웨어에 대한 것 전부 (`docs/tools.md` 4절)
- 분량: 15장 14,600자쯤, 16장 21,000자쯤, 17장 15,300자쯤. 목표를 20 - 25% 넘는다. 줄이지 않았고 단계 검토에서 본다
