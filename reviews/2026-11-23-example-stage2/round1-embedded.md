# 1차 검토: 임베디드 소프트웨어 엔지니어

역할: 자동차 제어기의 소프트웨어를 만들어 본 사람. 모델: Claude (Sonnet 5.5). 날짜: 2026-11-23.
FuSa 검토자의 기록은 보지 않았다. 규격에 관한 기억은 `(기억)`으로 표시했다. 읽은 것: proposal.md, example/drive-torque의 src, sim, test 구조, docs/technical-safety-concept.md, 단계 1의 round3-integration.md, disputes.md, RULES.md 8절, PLAN.md 8절.
시제품은 scratchpad의 복사본 (`design-embedded-s2/chain2.c`)에서 만들었다. 저장소는 고치지 않았다.

## 0. 결론

- 방향은 맞다. 그러나 열 가지를 다 넣는 것은 크다 (제품 .c가 328줄에서 약 950줄). M3, M7, M8을 줄이거나 문서로만 다루자.
- D2는 시제품에서 틈을 닫았다 (3절). 그러나 시제품이 단계 1의 기능에서 따로 문제를 하나 찾았다 (F-1).
- 가장 큰 걱정: 문서를 먼저 다 쓰고 코드를 나중에 쓰면, 묶음 2의 요구사항이 코드를 만들어 보기 전에 굳는다 (7절).

## 1. D1 - D8

| 번호 | 판정 | 이유와 안 |
|---|---|---|
| D1 | 수정 | M1, M2, M4, M5, M6, M9는 구현한다. M3은 속도와 inverter 수신 쪽 (받는 보호)만 구현하고 보내는 쪽은 문서로 둔다. M7은 변수 둘 (고정 플래그, counter)만. M8은 구현하되 최소 크기 (쓰기 한 번, 사본 둘)로. M10은 문서만 (진행자의 안에 동의). 이유는 5절의 크기 |
| D2 | 동의 (조건) | 시제품에서 입력 넷 모두 틈이 0 주기가 되었다. 조건: 기능의 F-1 (아래)을 먼저 고친다. 감시가 기능을 닮는 걱정은 맞다. 그래도 "감시의 한계는 요구사항에서 온다"는 원칙은 유지된다. 감시의 상한 250은 `SWR-06`에서 오고, 기능의 `RISE_PER_CYCLE`과 따로 둔다. 4절 순서에서 D2를 가장 먼저 넣자 |
| D3 | 동의 | 접점 둘의 브레이크 스위치는 자동차 제동등 스위치와 가속 override에 흔하다 (기억). 다만 EV는 제동 제어기가 CAN으로 주는 제동 압력이나 pedal 위치 신호가 더 흔하다 (기억). 가정을 "접점 둘, 또는 같은 신호를 다른 경로로 받는 입력 둘"로 넓게 쓰고, 예제는 접점 둘로 한다. 가정이 문제를 푸는 것처럼 보이는 위험은 "이 가정이 틀리면 M1은 아무것도 보장하지 않는다"를 가정 목록에 적어 줄인다 |
| D4 | 동의 (수정) | sim의 watchdog model은 "task를 건너뜀"과 "횟수나 순서가 틀림"만 잡는다. "늦음"은 흉내 낼 수 없다. scenario.h가 task의 실행 시간을 0으로 두기 때문이다. 늦음은 문서로만 다루거나, sim에 task마다 실행 시간을 더하는 model을 새로 둬야 한다 (크다). 전자를 권한다. model이 product와 같은 process에 있어 독립이 아님을 "못 보이는 것" 표 맨 위에 적는다 |
| D5 | 동의 | 속도가 없으면 "지금 기어 유지"는 맞다. 다만 기어 유지는 주행 중 R로 바뀜은 막지만 정차 중에도 N에서 D로 못 가는 거짓 차단을 만든다. 속도 timeout일 때 정지 상태 (마지막 속도 0)에 한해 바뀜을 받는 규칙은 속도 신호가 정지에 얼어붙은 고장에 약하다. 문서에 이 맞바꿈을 한 줄 적자 |
| D6 | 수정 | 55 Nm / 100 ms는 FTTI 200 ms에 빠듯하다: 판정 100 + 주기 10 + enable 전달 + inverter 응답 60 (기술안 5절의 값) = 약 170 ms. 여유가 30 ms다. 차이는 "토크 요구 대비"가 아니라 "요구의 최근 최댓값 대비"로 견줘야 한다. 요구를 0으로 내리면 inverter (시정수 20 ms)가 늦게 따라와 약 30 ms 동안 55 Nm를 넘는다 (250 Nm에서 계산). 그것은 100 ms 창 안에서 걸러지지만, 창을 줄이면 거짓 차단이 난다. 판정값은 예산에서 거꾸로 정하고 (창 = 200 - 10 - 전달 - 응답에서 여유를 뺀 값) 표로 보이자 |
| D7 | 동의 | 작은 형식 (4-bit counter, CRC-8, data ID)으로 충분하다. 실제 profile과 다르다는 것을 장에 밝힌다. CRC 다항식은 고른 이유를 적는다 (기억에 기대지 말고 예제용이라 밝힌다) |
| D8 | 동의 (조건) | SG-01만 끝까지 간다. 다만 H-04를 "요구사항으로 내리지 않는다"가 M10을 문서로만 둔다는 결정과 겹치므로 둘을 함께 쓴다: "맞바꿈을 보였지만 구현하지 않았다"를 안전 case의 열린 가지로 올린다 |

## 3. 시제품: D2가 단계 1의 틈을 닫는가

`chain2.c`: 단계 1의 기능 (`app.c` 그대로), 감시 둘 (단계 1의 것, 자기 변화율 상한을 가진 것). 기능이 틀린 경우는 "단계 1 감시가 허용하는 값을 요구"로 두었다. 입력은 round3 표의 넷이다 (400주기, 페달 100%). 단계 1의 숫자가 먼저 같게 나왔다 (재현).

| 입력 | 단계 1: 차이 55 Nm 이상 / 가장 긴 연속 | D2의 감시: 55 Nm 이상 / 가장 긴 연속 |
|---|---|---|
| 기어가 D 7주기, R 2주기 | 400 / 400 | 0 / 0 |
| 페달을 7주기 밟고 1주기 놓기 | 350 / 7 | 0 / 0 |
| 브레이크가 8주기마다 1주기 | 350 / 7 | 0 / 0 |
| 기어가 D 7주기, N 1주기 | 350 / 7 | 0 / 0 |

- 상한 250은 기능과 같은 값이다. 감시의 상태는 직전 주기의 상한과 방향이다 (약 12줄). 방향이 바뀌면 0에서 다시 오르는 규칙을 기능과 같게 갖는다.
- 틀린 기능이 허용 토크를 요구하면 감시가 깎고, 출력 단계의 고정이 5주기 뒤 걸린다 (넷 모두 latched=1). 단계 1은 고정조차 걸리지 않았다.
- 무작위 입력 10만 주기: D2는 55 Nm 이상의 틈이 0 주기. 단계 1은 3088 주기. 틈이 입력 모양에 달린 문제가 아님을 보인다.
- 정상 기능이 깎인 주기: 단계 1이 9, D2가 12 (아래 F-1). 고정에는 이르지 않았다 (5주기 이어져야 한다).

F-1 (새로 찾은 것, 단계 1의 기능): 기어가 D에서 R로 바뀔 때 페달이 낮으면 (예: 19.9%) 목표는 -19.8 Nm인데 기능이 -25 Nm를 낸다. `app.c`의 "else 분기"가 목표를 넘는 값을 내기 때문이다 (`(prev<0) ? ... : -RISE`가 목표와 견주지 않는다). 감시의 허용 (24.8 Nm)보다 크므로 한 주기 깎인다. 정상 기능이 자기 목표보다 큰 값을 내는 것이고, 단계 1의 test (`TC-011`)가 이 입력을 안 본다. 고치는 곳: `app.c`의 두 rise 제한을 `min(target, prev+RISE)` 꼴로 쓴다. D2를 넣기 전에 고친다. 더 이상 정상 기능이 깎이지 않음을 무작위 test로 확인한다.

D2 대안과의 견줌: 기능에서 제한을 빼면 틈이 늘 5 Nm가 되어 가장 단순하다. 그러나 토크가 한 번에 나가는 것 (승차감, 구동계 충격)을 책이 설명 없이 안전을 위해 받아들이게 된다. 가르치는 가치는 D2가 더 높다. 이 비교를 장에 표로 넣자.

## 4. 크기와 순서

크기 (제품 .c 기준): 지금 328줄 (app 57, monitor 93, vcu 75, input 18, pedal_check 85). 더함: M1 40, M2 40, M3 110, M4 40, M5 105, M6 70, M7 30, M8 105, M9 40, M10 50, D2 12 = 약 640. 합계 약 970. 헤더와 주석을 합하면 지금 572줄이 1600줄 안팎이 된다. 다 넣으면 3배다.
따라올 수 있는 크기: 한 모듈에 한 장이면 된다. 그러나 장 하나가 모듈 둘 이상을 넘으면 어렵다. 한 번에 넣을 때 독자가 따라가는 한도는 제품 .c 약 600줄 (두 배) 이내로 본다. 그래서 1절의 D1 수정 (M3의 보내는 쪽, M10, M7의 일부를 뺌)으로 약 800줄이 된다. 더 줄이려면 M7을 문서로만 하고 (-30), M3의 CRC를 속도 메시지 하나에만 쓴다.

순서 (각 단계 끝에 `make check`가 통과해야 한다):
1. F-1 수정, D2. 서로 얽힘 없음. `TC-011`에 무작위 입력 test를 더한다.
2. M9 (간헐 고장). 입력 검사에 닫힌다. 새 입력이 없다.
3. M1 (브레이크 둘). HAL에 입력 하나. 단계 4가 쓰지 않는다.
4. M3의 받는 쪽. 속도 메시지의 보호가 M2보다 먼저다 (보호 없이 속도를 믿는 중간 상태를 만들지 않는다). rx의 시그니처 변경은 sim과 test를 같은 commit에서 고친다.
5. M2. M3과 D5의 속도 timeout에 기댄다.
6. M4. M3의 inverter 수신 보호에 기댄다.
7. M5, 그다음 M6. M5가 task table을 바꾸므로 (task마다 표시) 앞의 것이 정착한 뒤에 넣는다. M6는 M5의 wdg interface와 enable 되읽기를 쓴다.
8. M7. 그 뒤 M8 (M7의 사본 규칙을 쓴다. 고정 플래그를 NVM에 쓰는 값이 사본 검사를 거치게).
얽힘: M2 -> M3(속도 보호) -> D5(속도 timeout). M4 -> M3(inverter 보호). M6 -> M5(wdg) 와 enable 되읽기. M8 -> M7 (고정 플래그), M8 -> reset 원인 (M5의 reset과 구분). 어느 단계도 `make check`를 못 지키는 순서는 없다. 위험한 곳은 4번 (시그니처 변경, 한 commit에 sim과 test가 함께 바뀜)이다.

## 5. 임베디드의 눈으로 본 틀리거나 어색한 곳

- debounce와 제동 우선: 주기가 10 ms (CYCLE_MS)다. debounce를 3주기 (30 ms)로 하면 제동의 반응이 30 ms 늦는다. 비대칭으로 해야 한다: "밟음"은 빨리 (한 접점이라도 밟음이면 1-2주기), "놓음"은 천천히 (두 접점이 합의하고 3주기). 놓음이 늦는 것은 H-01에 안전한 쪽이다. 대신 H-04 (예상치 못한 감속)에서는 방향이 반대다. 두 접점이 불일치한 채 이어지면 "밟음"으로 두고 고장으로 판정한다 (토크 0이므로 구동력이 없다). 이 맞바꿈을 장에 적는다.
- 접점 둘의 스위치: 흔하다 (제동등 스위치의 NO와 NC 쌍, 기억). 접점 둘이 한 connector와 한 전원을 공유하면 공통 원인은 남는다. 가정 목록에 쓴다.
- 질문과 답 watchdog: 흔한 방식이다 (기억). 그러나 "답을 task의 표시에서 계산한다"가 요점이다. 질문이 오고 답이 정해진 창 안에 가야 하는데, sim의 task 실행 시간이 0이므로 창의 아래쪽 (너무 빨리 답함)과 위쪽 (늦음) 모두 흉내가 뜻이 없다. 시험할 수 있는 것은 답의 값이 틀리거나 오지 않는 경우 (건너뜀)뿐이다.
- NVM에 고장 상태: 쓰는 도중의 전원 끊김은 사본 둘 (두 칸 번갈아 쓰기), 일련 번호, CRC로 막는다. 안전 경로에 쓰기를 넣지 않는다: 먼저 enable을 끊고 그다음 쓴다. 쓰기는 고정이 걸릴 때 한 번만 한다 (마모). 읽을 때 CRC가 틀리면 "고장 있음"으로 볼지 "기록 없음"으로 볼지가 정책이다. 전자는 가용성을 해치고 후자는 안전 쪽이 아니다. 어느 쪽인지 장에 적고 정비소에서 지우는 방법 (진단 명령)을 같이 둔다. 지우는 방법이 없으면 M8은 한번 걸린 차를 영구히 못 움직이게 만든다.
- 뒤집은 사본: 쓸 때마다 둘 다 갱신하는 규칙, 읽을 때 비교하는 규칙이 코드 곳곳에 퍼진다. 변수 둘에만 쓰고 접근 함수를 한 곳에 둔다. 최적화가 비교를 지우는 것은 -O0 sim에서 안 보인다. ECC가 있는 MCU에서는 중복이다. 그래서 "사본의 대상을 어떻게 고르는가"를 장에 쓴다 (고르는 기준이 없으면 장식이다).
- 켤 때의 자가 시험: 논리 시험은 몇 십 us라 문제가 아니다. enable을 켰다 끄는 시험은 inverter가 반응할 수 있으므로 토크 요구가 0일 때만 한다. 되읽기는 선의 전압이다. inverter가 실제로 구동을 끊었는지는 보지 못한다. 시험이 끝나기 전의 출력은 enable 꺼짐, 토크 0이어야 한다. 입력 검사의 ready (3주기 = 30 ms)와 같은 때에 끝나므로 시험 시간 때문에 시동이 늦지는 않는다. 길게 걸리는 시험 (RAM 전체)은 넣지 않는다.
- 독자가 오해하기 쉬운 것: 속도 신호를 감시의 입력에 더하면 감시가 "기능을 다시 계산하지 않는다"는 원칙이 흔들린다. D5의 속도는 기능과 감시 모두 쓰는가를 정해야 한다. 같은 속도 입력을 기능과 감시가 쓰면 공통 원인이다.

## 6. 4절 밖에서 빠진 것과 넣지 말 것

- 빠진 것: (a) 기능의 F-1 수정 (위). (b) 단계 시작 때의 reset 후 상태 (M8과 M5 중간). reset 직후 enable이 꺼진 채 시작함은 있다 (`SWR-12`). reset이 반복될 때 (watchdog reset의 연속)의 처리가 없다. 최소한 reset 횟수를 NVM에 세어 일정 횟수를 넘으면 고장으로 한다는 규칙을 문서에 둔다. (c) M5의 reset 후 감시의 자기 시험 결과를 진단 메시지로 내보내는 것 (hal_diag_t에 필드 몇 개).
- 넣지 말 것: M10의 구현, M7의 넓은 대상, M3의 보내는 쪽 구현.

## 7. 순서 (묶음 2 문서, 묶음 3 코드)

반대하지는 않으나 위험이 있다.
- 요구사항을 코드 없이 먼저 정하면 숫자 (debounce 주기, 창, 한계값)가 틀린 채 굳는다. 이번 시제품만 해도 F-1 (기능이 목표를 넘음)과 D6의 여유 30 ms는 코드와 숫자를 돌려 보고서야 보였다. 묶음 3에서 요구사항을 고치게 되면 묶음 2의 문서 (HARA, FSC, TSC, HSI)가 함께 고쳐진다.
- 제안: 묶음 2에 "숫자는 임시, 묶음 3의 측정이 확정" 표시를 두고, 숫자가 걸린 요구사항은 묶음 3이 끝난 뒤 한 번에 닫는다. 또는 D2와 M9 (코드가 작고 얽힘이 없음)만 묶음 2에서 먼저 구현한다.
- 문서 장 (8, 9장)이 코드 없이 나가면 독자가 "문서가 코드와 어긋남"을 보는 것이 아니라 문서만 읽는다. 그러나 이 책의 요점은 요구사항이 코드와 test로 추적된다는 것이다. 묶음 2의 문서가 가리킬 코드 위치가 비어 있는 동안 `tools/trace.py`의 추적 검사에서 요구사항이 test 없이 남는다. 이를 "구현 예정" 상태로 허용하는 규칙이 필요하다.
