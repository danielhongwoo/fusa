# 설계안: 단계 2에서 예제를 넓히는 범위

진행자 (Claude 주 세션)가 쓴 안이다. 두 검토자가 토론한다 (PLAN.md 9절: 3회까지, 합의되지 않으면 진행자의 안으로 진행하고 쟁점을 모아 저자에게 알린다).

## 1. 이미 정해진 것 (토론하지 않는다)

- 책 전체에서 끌고 가는 hazard는 `H-01` (의도하지 않은 가속) 하나다. 나머지 넷은 6장의 표와 7장의 safe state 논의에만 쓴다 (scope.md. 저자가 2026-11-22에 "scope.md대로"라고 정했다).
- item의 경계는 VCU 하나다. inverter는 가정으로 받는다.
- 보드나 emulator로 옮기지 않는다. PC 시뮬레이션까지 한다.
- 검사 counter는 이어지는 횟수를 유지하고, 간헐 고장을 따로 판정하는 검사를 더한다.
- fault는 HAL의 뒤에서 넣거나 모듈을 link할 때 바꿔 끼워 넣는다. 제품의 소스에 test용 코드를 넣지 않는다.
- 실행 모델: thread 하나, 1 ms 가상 시계, 정적 task table.

## 2. 단계 1이 남긴 것

safety case의 열린 가지 넷과 알려진 한계다.

| 번호 | 남긴 것 | 지금의 상태 |
|---|---|---|
| G5 | 감시와 출력 단계 자신의 고장 | 논증하지 않았다 |
| G6 | item 밖의 요소 (inverter)가 가정대로 동작한다 | 가정뿐이다. VCU는 실제 토크를 보지 않는다 |
| G7 | 브레이크와 기어의 입력 | 한 채널이고 검사하지 않는다. debounce도 없다 |
| G8 | 토크 요구의 전송 | 메시지의 보호가 없다 |
| L1 | 입력의 간헐 고장과 기능의 고장이 겹침 | 기능의 변화율 제한을 감시가 따라가지 않아 틈이 이어진다 |
| L2 | reset이 고장 상태를 지운다 | 고장 상태가 RAM에만 있다 |
| L3 | 페달 채널 하나의 고장에도 토크 0 | 줄여서 계속 가는 상태 (safe state의 1단계)가 없다 |
| L4 | 실행의 고장 | task를 건너뛰거나 늦는 경우를 넣어 본 적이 없다 |

## 4. 더하는 mechanism (안)

| 번호 | mechanism | 닫는 것 | 새로 필요한 가정이나 HAL |
|---|---|---|---|
| M1 | 브레이크 신호의 검사: 접점 둘 (밟으면 닫히는 것과 열리는 것)을 서로 견준다. 둘 다 debounce한다 | G7 | 브레이크 스위치가 접점 둘을 준다는 가정. digital 입력 하나 추가 |
| M2 | 기어 신호의 검사: 유효한 부호만 받는다. 차량 속도가 일정 값 위일 때 D와 R 사이의 바뀜을 받지 않는다 | G7, 단순화 "주행 중에 R로 바뀜" | 차량 속도를 다시 읽는다. 속도 메시지의 timeout과 보호가 필요하다 |
| M3 | 토크 요구 메시지의 보호: counter와 CRC, data ID. 받는 메시지 (속도, inverter 상태)에는 timeout과 같은 보호 | G8 | inverter가 보호를 검사한다는 가정 |
| M4 | 실제 토크를 되읽어 견준다: inverter가 알린 토크가 보낸 토크 요구보다 오래 크면 구동 허용 신호를 끊는다 | G6의 일부 | `hal_can_rx_inverter`를 쓴다 |
| M5 | 감시의 실행을 감시한다: task마다 지나간 표시를 남기고 (program flow), 주기의 끝에서 순서와 횟수를 확인해 외부 watchdog에 답한다. 답이 틀리거나 늦으면 watchdog이 구동 허용 신호를 끊는다 | G5, L4 | 외부 watchdog의 model을 sim에 둔다 (`A-10`을 흉내). HAL에 watchdog interface |
| M6 | 켤 때의 자가 시험: 깎기와 고정의 논리를 알려진 입력으로 돌려 본다. 구동 허용 신호를 끊을 수 있는지 되읽어 확인한다 | G5 (숨은 고장) | 구동 허용 신호의 되읽기 입력 |
| M7 | 중요한 변수의 보호: 고장 상태와 counter를 뒤집은 사본과 함께 둔다. 어긋나면 safe state | G5 (메모리의 bit 반전) | sim에서 고른 변수의 bit를 뒤집는 fault |
| M8 | 고장 상태를 비휘발성 memory에 적는다. 켤 때 읽어 고장이 남아 있으면 구동을 허용하지 않는다 | L2 | HAL에 비휘발성 memory와 reset 원인 |
| M9 | 간헐 고장의 판정: 최근 N주기 가운데 실패가 M번을 넘으면 고장 | L1의 일부, disputes 1번의 결정 | 없다 |
| M10 | 줄여서 계속 가기: 페달 채널 하나만 고장이고 다른 채널이 범위 안이면 그 채널로 토크를 제한해 계속 간다 | L3 (`H-04`와의 맞바꿈) | 없다 |

## 5. 토론할 것

| 번호 | 물음 | 진행자의 안 | 걱정 |
|---|---|---|---|
| D1 | 4절의 열 가지를 다 넣는가 | 다 넣는다. 다만 M10은 문서에서 맞바꿈만 논하고 구현은 마지막에 정한다 | 예제가 너무 커져 독자가 따라가지 못한다. 지금 제품 코드는 약 300줄이다 |
| D2 | L1 (변화율의 틈)을 어떻게 닫는가 | 감시가 자기 변화율 상한을 갖는다: 허용 토크가 한 주기에 올라갈 수 있는 양을 기능과 같은 값으로 제한한다. 감시에 상태 하나가 생긴다 | 감시가 기능을 닮아 간다. 대안은 기능에서 제한을 빼는 것 (틈이 늘 5 Nm)이나, M9와 debounce로 조건만 줄이는 것 |
| D3 | M1의 가정 (접점 둘)을 item 밖의 가정으로 더해도 되는가 | 더한다. 보고서가 브레이크 신호의 검사를 요구사항으로 든다 (nhtsa-etc-ev-fsa 81쪽) | 가정을 늘려 문제를 푸는 것처럼 보인다 |
| D4 | M5의 외부 watchdog을 어디까지 흉내 내는가 | sim에 작은 model을 둔다: 정해진 창 안에 옳은 답이 오지 않으면 구동 허용 신호를 끊는다. "독립성은 시뮬레이션되지 않는다"는 것을 그대로 적는다 | 흉내 낸 것을 보고 독립이 보였다고 읽을 위험 |
| D5 | M2에서 속도를 다시 읽으면 속도 신호의 고장이 새 가지가 된다. 받아들이는가 | 받아들인다. 속도가 없으면 기어의 바뀜을 받지 않는 쪽 (지금 기어를 유지)으로 간다 | 감시의 입력이 늘어난다. 단계 1에서 일부러 뺀 것을 되돌린다 |
| D6 | M4의 판정값 | 차이 55 Nm가 100 ms 이어지면 차단 | inverter의 응답 지연과 겹쳐 거짓 차단이 날 수 있다 |
| D7 | M3의 보호를 어떤 모양으로 하는가 | 이 책의 작은 형식 (4-bit counter, CRC-8, data ID). AUTOSAR의 E2E 문서를 근거로 든다 | 실제 profile과 다르다는 것을 밝혀야 한다 |
| D8 | safety goal을 더 세우는가 | `SG-01`만 끝까지 간다. `H-04`에는 safety goal을 적되 요구사항으로 내리지 않고, M10과 safe state의 논의에서만 쓴다 | `H-04`를 요구사항 없이 논하면 맞바꿈이 말로만 남는다 |

## 6. 검토자에게 묻는 것

1. D1 - D8마다: 동의 / 수정 / 반대, 그리고 이유.
2. 4절에 빠진 mechanism이 있는가. 넣지 말아야 할 것이 있는가.
3. 3절의 순서가 맞는가. 문서 (묶음 2)와 코드 (묶음 3)를 나누는 것이 맞는가.
4. 이 범위에서 책이 잘못 가르칠 위험이 가장 큰 곳은 어디인가.
