## 1. 시제품: I1의 모양 (기능은 F-1을 고친 것)

감시: 허용 = min(페달 상한 (단계 1의 허용 토크, 오차 5 Nm 포함), 지난 출력의 크기 + R_m). 지난 출력의 부호가 지금 기어의 방향과 다르면 크기 0. 입력은 round1의 넷 (400주기, 페달 100%)과 무작위 10만 주기 (seed 1).
틀린 기능 둘: A = 페달 상한까지 요구 (깎이고 고정된다), B = 허용 토크를 그대로 요구 (깎이지 않고 고정도 안 된다. 감시가 막아야 하는 최악이다). 차이 = 틀린 기능의 출력 - 정상 기능의 토크 (기어 방향, 초과분만).

| 입력 | R_m (Nm) | (a) 정상 기능이 깎인 주기 | (b) B: 55 Nm 이상 주기 / 가장 큰 차이 | A: 55 Nm 이상 / 가장 큰 차이 | (c) 고정 |
|---|---|---|---|---|---|
| 기어 D 7, R 2 / 페달 7 밟고 1 놓음 / 브레이크 1 of 8 / D 7, N 1 | 25 | 0 (넷 모두) | 0 / 0 Nm (넷 모두) | 0 / 0 Nm | A는 5번째 주기 (50 ms). B는 아니다 |
| 같은 넷 | 26 | 0 | 0 / 7 Nm | 0 / 4 Nm | 같음 |
| 같은 넷 | 30 | 0 | 0 / 35 Nm | 0 / 20 Nm | 같음 |
| 무작위 10만 | 25 | 0 | 0 / 5 Nm | 0 / 5 Nm | A는 256번째 주기에 고정 (입력이 처음 5주기 이어서 깎이는 때) |
| 무작위 10만 | 26 | 0 | 0 / 13 Nm | 0 / 9 Nm | 같음 |
| 무작위 10만 | 30 | 0 | 0 / 40 Nm | 0 / 25 Nm | 같음 |

- 비교: 단계 1의 감시는 같은 입력에서 (400, 350, 350, 350)주기가 55 Nm 이상, 무작위에서 3088주기 (앞 회의 측정).
- (a) F-1을 고치지 않으면 정상 기능이 깎인다 (앞 회의: 무작위에서 9주기). 고친 뒤에는 0이다. 고친 곳: 두 rise 제한을 `min(목표, max(prev,0)+R_f)` 꼴로.
- R_m이 R_f보다 큰 만큼 틈이 주기마다 쌓이다가 페달 상한에서 멈춘다. 가장 큰 차이의 어림: 오차 + TORQUE_MAX x (R_m - R_f) / R_m (30 Nm에서 40 Nm, 측정과 맞다). 55 Nm 예산에서 R_m은 R_f + 약 5 Nm까지다. 예산표에 이 식을 넣자. 같은 값 (25)이 가장 안전하고, 값을 달리 두는 이유는 "기능을 바꿔도 감시가 따라 바뀌지 않게"뿐이다.
- 지난 출력의 되먹임은 고정 뒤에도 맞다: 고정되면 출력 0, 다음 허용은 R_m이다.
- 새 틈 하나 (FuSa가 찾을 곳): 지난 출력이 한 주기 망가지면 (bit 반전) 허용이 페달 상한까지 한 주기 뛴다. 다음 주기에 출력으로 덮어쓰이므로 10 ms 한 번이고 FTTI 200 ms보다 짧다. 그래서 지난 출력은 M7의 대상에서 뺄 수 있다 (4절).

## 3. I3: plant의 inverter 검사와 전송 중의 고장

현재 구조: `hal_can_tx_torque(torque_t)`가 plant에 값을 곧바로 넘긴다 (hal_sim.c 101행). 바꿀 것: tx를 frame 구조 (값, counter, data ID, CRC)로.
- 제품: e2e.c +55 (CRC-8, counter, ID, 검사 함수. rx 쪽과 함께 쓴다), vcu.c +10, hal.h +15.
- sim: hal_sim.c +35 (전송 중의 고장 셋: 값이 바뀜, 직전 frame을 되풀이, 멈춤), plant.c +25 (inverter 쪽의 CRC와 counter와 ID 검사, 거부가 이어지거나 timeout이면 목표 토크 0), scenario와 fault 목록 +5. 합 약 +65.
- test +80. 대조 test: plant의 검사를 끈 시나리오 (sim의 설정 하나)에서 값이 바뀜은 `SG-01`을 어기고, 보호를 켜면 안 어긴다. 보여 줄 수 있다.
- 한계 (적을 것): "보호를 켜면 안 어긴다"는 내가 쓴 inverter 모델의 규칙을 확인할 뿐이다. 보이는 것은 "보호가 없으면 어긴다"와 "VCU의 frame이 규칙대로 만들어졌다"이다. 실제 inverter가 검사한다는 것은 가정 (`A-17`)으로 남는다.

## 5. I15: 추적 검사

trace.py의 검사 3과 4 (src의 ID, test의 TC)가 SWR 전부에 걸려 있다. 고칠 것 (약 25줄):
1. requirements.yaml에 `status: planned`와 `planned_in: 3` (묶음 번호)를 허용한다 (parser는 이미 임의의 키를 읽는다).
2. planned인 SWR은 src와 test의 존재를 요구하지 않는다. 대신 parents, text, verified_by (계획한 TC 이름)는 요구한다.
3. 거꾸로: planned인데 src에 ID가 있거나 TC가 test에 있으면 문제다 ("구현됨인데 planned"). 상태가 낡는 것을 막는다.
4. 출력에 "구현 예정 N개"와 ID 목록을 항상 찍는다. 조용히 남지 않는다.
5. `--final` (또는 make check STRICT=1)이면 N > 0이 실패다. 묶음 3의 끝에서 STRICT=1로 돌려 0임을 확인한다.
6. safety-case.md가 planned인 요구사항을 증거로 가리키면 문제로 한다 (문서 검사 10줄이면 된다).

## 6. 쟁점

- I9의 창: 통합안의 80 ms는 200 ms 안에 안 든다 (계산). 창 50 ms로 줄이자. 근거: inverter가 요구를 무시하는 경우의 합 210 ms.
- M7과 850줄: 지난 출력은 M7에서 빼고, 줄이 모자라면 M7 전체를 문서로. 근거: 지난 출력은 매 주기 덮어쓰이는 값이다 (10 ms 한 번의 영향).
- I3의 대조 test는 반만 증거다: 장에 "내가 쓴 inverter 모델이 확인한 것"이라고 적자.
