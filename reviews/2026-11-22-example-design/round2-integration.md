# 2차: 통합안

1차 의견 두 개 (`round1-fusa.md`, `round1-embedded.md`)를 합친 안이다. 진행자 (Claude 주 세션)가 썼다. 두 검토자는 항목마다 동의하는지 답한다.

1차의 결과
- T1, T3, T4, T5는 두 검토자의 방향이 같다. T5는 둘 다 설계안이 아닌 다른 안 (link할 때 결함 모듈로 바꿔 끼움)을 골랐다.
- T2는 서술이 갈린다. FuSa 전문가는 "SG-01에 대해서"라는 한정과 입력 경로의 할당을, 임베디드 엔지니어는 "같은 곳에 실리므로 개발은 같은 등급"이라는 서술을 양보할 수 없다고 했다.
- 쟁점 밖의 지적 10개는 서로 부딪치지 않는다. 다만 구조를 바꿔야 풀리는 것이 있다 (I6).

## 통합안

### I1. 감시가 출력을 깎는다 (T1)

- 안 A를 쓴다. 출력 단계가 매 주기 토크 요구를 허용 토크로 깎는다. 넘는 토크는 한 주기도 나가지 않는다.
- 깎기와 고정 판단을 함수로 나눈다. 깎인 횟수를 센다.
- 기능의 출력은 깎기 전의 값으로 따로 test한다.
- 본문에서 안 B (지켜보기만 함)를 대비로 설명한다. 깎기가 기능의 결함을 가리는 대가와 감시 자신의 한계도 적는다.
- 시간 예산표는 두 줄이다: 넘는 토크가 출력에 나가지 않게 되는 시간, 기능을 고장으로 판정하고 구동 허용 신호를 끊는 시간.

### I2. 등급 할당의 서술 (T2)

- `SG-01`의 안전 요구사항은 입력 검사 (페달, 브레이크, 기어를 읽고 검사하는 부분), 감시 (허용 토크), 출력 단계 (깎기, 고정, 구동 허용 신호)에 준다.
- 기능에는 "`SG-01`에 대해서" 안전 요구사항을 주지 않는다. 기능이 토크를 덜 내는 것 (`H-04`, `H-05`)은 감시가 막지 못한다. 예제는 그 hazard를 끌고 가지 않는다는 것을 같은 자리에 적는다.
- ASIL decomposition은 쓰지 않고, 쓰지 않는 이유를 적는다.
- 등급이 다른 소프트웨어를 함께 실을 때의 두 길을 `(2차 자료)`로 소개한다. 근거는 `autosar-safety-measures` 9쪽 (ISO 26262:2018 기준)과 `nhtsa-etc-ev-fsa` 73쪽, 80쪽 (FDIS 2011 기준)이다.
- 예제의 선택을 이렇게 적는다: "실제 제어기에서는 메모리 보호와 실행 감시로 방해가 없음을 보이거나, 기능도 같은 등급으로 개발한다. PC 시뮬레이션은 방해가 없음을 보일 수 없다. 그래서 예제는 기능의 코드에도 같은 개발 방법 (compiler 경고, 정적 분석, test, coverage 측정)을 적용한다. 요구사항 추적에서 `SWR-`은 입력 검사, 감시, 출력 단계에만 달린다."
- "QM"이라는 말은 이 문맥에서 쓰지 않는다.

### I3. 페달을 믿을 수 없으면 토크 0 (T3)

- 뼈대에서는 토크 0만 구현하고, 같은 대응에 경고 요청을 넣는다.
- 본문에 적는 것: 이 예제에는 회생 제동과 creep이 없어서 토크 0은 타력 주행이다. 보고서는 두 채널 고장에 "페달 없이 낮은 속도로 움직일 수 있는 상태"를 든다. 토크 0은 `H-04`와 맞바꾸는 선택이다.
- 복귀 규칙: 페달 고장과 기능 고장의 고정은 다시 켤 때까지 유지한다.

### I4. HARA의 값 (T4)

- S, E, C의 값을 적는다. "보고서가 비슷한 상황에 준 값을 빌린 가정"이라는 말은 표 머리에 한 번 적는다. 줄마다 이유를 한 문장 적는다.
- 가장 나쁜 줄은 S3, E4, C3에서 D가 나온다고 풀어 적고 `(2차 자료)`로 밝힌다 (`nhtsa-etc-ev-fsa` 55-56쪽).
- 정지 상황과 고속 상황을 둘 다 넣는다. 후륜 C3, 전륜 C2의 예와, 분석자마다 등급이 달랐다는 주석을 함께 적는다.
- 등급을 찾는 표는 옮기지 않는다. 확률이나 빈도의 수치는 쓰지 않는다.

### I5. 기능의 고장은 link할 때 바꿔 끼운다 (T5)

- 결함이 있는 기능 모듈을 `test/`에 두고 Makefile에서 `app.c` 대신 link한다. 제품 소스에는 `#ifdef`나 갈고리 함수를 넣지 않는다.
- 결함 모듈은 둘이다: 크게 내는 것, 작게 내는 것.
- 원칙의 문장을 바꾼다: "fault는 HAL의 뒤에서 넣거나, 모듈 전체를 link로 바꿔 끼워서 넣는다. 제품의 object file에는 test 코드가 없다."
- RAM의 bit 반전은 단계 1에서 하지 않는다. "sim이 못 보이는 것" 표에 올린다. 이 test의 결과를 freedom from interference의 증거로 쓰지 않는다.

### I6. 구조: 입력 검사를 따로 둔다

1차의 두 지적 (입력 경로를 할당에 넣을 것, 페달 고장 대응과 고정 판단이 겹쳐 거짓 고정이 나는 것)을 풀려고 구조를 바꾼다.

1. 입력 읽기: 주기마다 한 번, 입력 구조체 하나를 만든다 (값과 상태)
2. 입력 검사: 페달 두 채널을 같은 단위 (0-1000)로 환산하고, 범위와 서로의 차이를 검사해 안전한 페달 값과 유효 여부를 낸다
3. 기능: 안전한 페달 값으로 토크 요구를 만든다
4. 감시: 같은 안전한 페달 값, 브레이크, 기어로 허용 토크를 계산한다
5. 출력 단계: 깎기, 고정 판단, 송신

- 기능과 감시가 같은 안전한 페달 값을 쓰므로, 고장이 없을 때 토크 요구는 허용 토크를 넘지 않는다. 페달 고장이면 안전한 페달 값이 0이 되어 기능도 0을 요구한다. `FI-01`에서 고정이 일어나지 않는다는 것을 test한다.
- 대가: 입력 검사는 기능과 감시가 함께 기대는 지점이다. 그래서 `SG-01`의 요구사항을 받는다. 감시가 따로 계산하는 것은 코드의 분리이지 입력의 분리가 아니라고 적는다.

### I7. 허용 토크와 오차

- 단위: 페달 0-1000, 토크 0.1 Nm, 모두 `int32_t`. 곱하기 전에 입력을 범위로 자른다. 나눗셈은 내림이다.
- 허용 토크는 안전한 페달 값에 비례하는 상한이다. 속도에 따른 토크 감소는 넣지 않는다 (감시는 기능을 다시 계산하지 않고 상한만 계산한다).
- 다음 가운데 하나면 허용 토크는 0이고 오차도 더하지 않는다: 안전한 페달 값이 놓음 구간 (30) 아래, 브레이크를 밟음, 기어가 P 또는 N.
- 그 밖에는 오차를 더한다. 오차는 최대 토크의 2% (5 Nm)다. 기능도 같은 놓음 구간을 쓴다.

### I8. 시간

- 200 ms를 FTTI라고 부르지 않는다. "safe state에 도달하는 시간의 한계 (예제의 가정값)"이라고 부른다. FTTI와의 관계는 7장에서 받은 문서의 쓰임을 근거로 설명하고, 정의를 단정하지 않는다.
- `SG-01`은 차량의 결과로 적는다: "운전자의 요구보다 1.0 m/s^2 넘게 큰 가속이 200 ms 넘게 이어지지 않게 한다 (두 값은 가정)". 토크의 오차는 아래 단계의 요구사항으로 내린다.
- debounce는 주기의 수로 정한다. 페달 불일치는 3주기 연속이면 고장이다. 토크 요구의 초과는 5주기 연속이면 고정한다.
- 시간 예산표에 넣는 것: 고장이 난 때부터 다음 주기까지 (최대 10 ms), debounce, CAN 전송 (가정), inverter의 토크 응답 (가정 `A-05`), 구동 허용 신호의 지연 (가정).
- fault를 주기 안의 0-9 ms 위치에 넣어 가며 가장 나쁜 시간을 재는 test를 둔다.

### I9. 감시 자신의 고장

- 단계 1: FTA와 독립성 주장 목록에 "감시의 고장"과 "숨은 고장"의 가지를 적는다. 가정 `A-10`의 감시 요소는 살아 있는지만 본다는 한계를 적는다. 감시를 다른 함수에 둔 것은 독립이 아니라고 다시 적는다.
- 단계 2 (8장, 12장)로 미루는 것: 켤 때 깎기와 구동 허용 차단을 시험하는 자가 시험, "감시의 고장과 기능의 고장이 겹침"을 넣는 fault injection.

### I10. fault injection의 목록

| ID | fault | 넣는 곳 | 기대 |
|---|---|---|---|
| `FI-01` | 페달 채널 1이 높은 값에 고착 | HAL | 3주기 안에 페달 고장 판정, 토크 0, 경고 요청. 기능 고장의 고정은 일어나지 않는다 |
| `FI-02` | 기능이 너무 큰 토크를 요구 | 결함 모듈 | 출력은 한 주기도 허용 토크를 넘지 않는다. 5주기 뒤에 고정하고 구동 허용 신호를 끊는다 |
| `FI-03` | 두 채널이 같은 비율로 올라감 | HAL | 알아채지 못한다. "두 채널이 일치하면 믿는 비교 검사의 한계"로 적는다 |
| `FI-04` | 페달을 놓고 서 있는데 기능이 작은 토크를 요구 | 결함 모듈 | 출력은 0이다 |
| `FI-05` | 기능이 토크를 덜 냄 | 결함 모듈 | 감시는 알아채지 못한다. `SG-01`의 범위 밖임을 보이는 test다 |

- 차량 속도 메시지가 끊기는 fault는 단계 1에서 뺀다. 감시가 속도를 쓰지 않기 때문이다. 단계 2에서 안전 요구사항과 무관한 robustness 시험으로 따로 표시해 넣는다.

### I11. HAL과 시간의 단위

- 입력은 주기마다 한 번 읽어 구조체 하나에 담는다. CAN 수신에는 나이를 함께 둔다.
- 입력 검사와 감시는 시간을 주기의 수로만 센다.

### I12. 시뮬레이션의 시간 모델

- 문서에 적는다: 1 ms마다 운전자 입력, fault 적용, 센서와 메시지 갱신, (10 ms마다) task table 실행, plant 진행, 기록의 순서로 돈다.
- 실행 시간은 0이다. jitter와 마감 초과는 보이지 못한다.

## 답하는 형식

- I1-I12마다 "동의" 또는 "반대"를 적는다. 반대면 이유와 고칠 문장을 적는다.
- 동의하지만 꼭 덧붙일 조건이 있으면 한 줄로 적는다.
- 60줄을 넘기지 않는다.
