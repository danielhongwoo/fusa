# 토론 기록: 관통 예제의 설계 (2026-11-22)

## 대상

단계 0.5와 단계 1에서 만들 예제의 설계안 ([proposal.md](proposal.md)). 저자가 "확인이 필요한 것은 에이전트끼리 토론하고, 3회 안에 합의되지 않으면 우선 진행한 뒤 쟁점을 모아 알려 달라"고 정한 뒤의 첫 토론이다.

|---|---|---|

## 결과

합의된 것 (I1-I12, I7은 수정안)
- 출력 단계가 매 주기 토크 요구를 허용 토크로 깎는다. 계속 넘으면 기능의 고장으로 고정하고 구동 허용 신호를 끊는다
- `SG-01`의 안전 요구사항은 입력 검사, 감시, 출력 단계에 준다. 기능에는 "`SG-01`에 대해서" 주지 않는다. ASIL decomposition은 쓰지 않는다
- 페달을 믿을 수 없으면 토크 0으로 간다. 이것이 `H-04`와 맞바꾸는 선택이라는 것을 본문에 적는다
- HARA의 S, E, C는 보고서의 값을 빌린 가정으로 적는다
- 기능의 고장은 결함이 있는 모듈을 link할 때 바꿔 끼워서 넣는다 (설계안과 다른 안으로 합의)
- 입력 검사를 따로 두고, 기능과 감시가 같은 안전한 페달 값을 쓴다
- 200 ms를 FTTI라고 부르지 않는다. `SG-01`은 차량의 결과 (가속의 차이와 시간)로 적는다
- 감시 자신의 고장은 단계 1에서 논증하지 않고, safety case에 닫히지 않은 가지로 남긴다

3차에서 더해진 것 (반대 없이 받아들임)
- 허용 토크의 식은 선형이고, 기능의 토크는 그 식을 넘지 않아야 한다
- 기어 값을 알 수 없으면 N으로 본다
- 주행 중에 기어 신호가 R로 바뀌는 경우를 단순화 목록과 FTA에 적는다

합의되지 않은 것 (1건)
- 검사 counter의 규칙
  - 임베디드 엔지니어: 실패가 N주기 이어지면 고장이고, 한 주기라도 통과하면 0으로 되돌린다. 가장 나쁜 시간이 N x 10 ms로 닫힌다. 간헐 고장을 놓치는 것은 뼈대의 한계로 적는다
  - FuSa 전문가: 실패하면 1 올리고 통과하면 1 내린다. 이어지는 counter는 실패와 통과가 번갈아 나오는 간헐 고장을 끝내 판정하지 못하고, 독자가 그대로 따라 쓰기 쉽다. 이어지는 counter를 유지한다면 그 한계를 본문에 적는 것이 최소 조건이다
  - 진행자의 결정: 단계 1은 이어지는 counter로 간다. 한계를 요구사항 문서와 12장에 적는다 (FuSa 전문가의 최소 조건). 12장을 깊게 고치는 단계 2에서 다시 정한다
  - 저자에게 알릴 쟁점으로 `notes/disputes.md`에 올렸다

## 확인하지 못한 것

- 두 검토자 모두 ISO 26262의 원문을 보지 못했다. 규격에 관한 말은 "기억에 의존, 미확인"으로 표시되어 있다.
- 두 검토자는 같은 계열의 모델이다. 의견이 일치한 것을 사실 확인으로 여기지 않는다.
