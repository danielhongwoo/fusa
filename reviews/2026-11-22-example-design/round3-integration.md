# 3차: I7의 수정안과 받아들인 조건

2차의 결과
- I1-I6, I8-I12는 두 검토자가 모두 동의했다. 붙인 조건은 아래 "받아들인 조건"에 모았다.
- I7은 두 검토자가 모두 반대했다. 이유는 서로 다르고 부딪치지 않는다.
  - FuSa 전문가: 브레이크를 밟으면 허용 토크가 0인 것은 보고서의 제동 우선과 다르고, 브레이크 신호가 고착되면 `H-04`가 된다. 단순화라고 밝혀야 한다.
  - 임베디드 엔지니어: 방향 (기어 R)이 빠져 있다. 오차를 5%에서 2%로 바꾼 이유가 없다. 기능이 입력의 변화를 한 주기 안에 반영해야 한다.

## I7 수정안: 허용 토크와 오차

- 단위: 페달 0-1000, 토크 0.1 Nm, 모두 `int32_t`. 곱하기 전에 입력을 범위로 자른다. 나눗셈은 내림이다.
- 허용 토크는 크기 (0 이상)의 상한이고, 안전한 페달 값에 비례한다. 속도에 따른 토크 감소는 넣지 않는다. 식은 기어 D와 R에서 같다.
- 방향은 기어가 정한다. D에서는 0 이상 허용 토크 이하, R에서는 허용 토크의 음수 이상 0 이하만 나간다. P와 N에서는 0만 나간다. 부호가 틀린 요구도 깎고, 초과로 센다.
- 다음 가운데 하나면 허용 토크는 0이고 오차도 더하지 않는다: 안전한 페달 값이 놓음 구간 (30) 아래, 브레이크를 밟음, 기어가 P 또는 N.
- 그 밖에는 오차 5 Nm (최대 토크 250 Nm의 2%)를 더한다. 설계안의 5%에서 바꾼 이유: 기능과 감시가 같은 안전한 페달 값을 쓰게 되어 (I6) 오차가 덮을 것이 계산의 반올림뿐이다. 이 오차가 `SG-01`의 가속 한계 안에 드는지는 차량의 가정값으로 계산해 technical safety concept에 적는다.
- 브레이크를 밟으면 허용 토크가 0인 것은 예제의 단순화다. 보고서의 제동 우선은 속도 조건과 예외를 둔다. 브레이크 신호는 한 채널이어서 "밟음"에 고착되면 `H-04`가 된다. 이것을 6장의 표와 FTA에 적는다.
- 기능은 브레이크, 놓음 구간, 기어의 변화를 같은 주기 안에 반영한다. 토크를 내릴 때는 기울기를 쓰지 않는다. 정상인 기능이 모든 입력에서 깎이지 않는다는 것을 test한다.

## 받아들인 조건

진행자가 모두 받아들였다. 서로 부딪치는 것은 없다고 보았다.

| 항목 | 조건 | 낸 쪽 |
|---|---|---|
| I1 | "넘는 토크는 한 주기도 나가지 않는다"는 VCU 소프트웨어의 논리에 대한 성질이다. 하드웨어의 고장, compiler의 오류, 주기를 놓치는 경우는 덮지 않는다. "증명"이라는 말을 쓸 때 같은 문장에 범위를 적는다 | FuSa |
| I1 | 깎인 횟수와 고장 상태는 HAL의 진단 출력으로 내보낸다. 시뮬레이션은 VCU를 HAL의 출력으로만 본다 | 임베디드 |
| I2 | 방해가 없음을 보이는 범위를 "메모리, 시간과 실행, 정보 교환"으로 적는다. 같은 MCU의 하드웨어 공통 고장은 `A-10`에 기댄다고 적는다 | FuSa |
| I2 | "같은 개발 방법을 적용한다" 뒤에 "이 방법이 규격이 그 등급에 요구하는 것을 채우는지는 확인하지 않았다"를 붙인다. "기능이 토크를 덜 내는 hazard를 끌고 갔다면 기능도 안전 요구사항을 받는다"를 한 줄 더한다 | FuSa |
| I2 | "같은 개발 방법"의 목록은 `make check`가 기능의 코드에 실제로 돌리는 것과 맞춘다 | 임베디드 |
| I3 | 토크 0으로 가는 방법은 계단 (바로 0)이라고 요구사항에 적는다. "다시 켤 때까지 유지"는 뼈대의 단순화이고 `H-04`의 대가라고 적는다. 다시 켠 뒤에는 입력 검사가 통과하기 전에 토크를 허용하지 않는다 | 둘 다 |
| I3 | "토크 0은 감속이 작다"고 쓰지 않는다. "회생 제동이 없어 감속은 페달을 뗀 것과 같다"까지만 쓴다 | FuSa |
| I4 | 분석자마다 등급이 달랐다는 주석의 쪽은 57이다 | FuSa |
| I5 | 결함 모듈은 `app.h`의 같은 interface를 구현하고 같은 compile 옵션으로 만든다. coverage 측정에서 뺀다 | 임베디드 |
| I6 | FTA에서 입력 검사를 "기능과 감시가 함께 기대는 단일 지점"으로 그린다. 기능이 안전한 페달 값을 쓰면서 감시는 페달 경로의 고장을 잡지 못한다는 대가를 적는다 | FuSa |
| I6 | 불일치 counter의 규칙: 검사에 실패한 주기가 이어지면 올리고, 한 주기라도 통과하면 0으로 되돌린다. 고장으로 판정한 뒤에는 유지한다 | 임베디드 |
| I8 | 센 규칙: "N번째로 이어서 고장을 본 주기에, 그 주기의 출력부터 반영한다". 초과는 "한 번이라도 깎였으면"이다. 한 주기 정상이면 counter는 0이다 | 임베디드 |
| I8 | `SG-01`의 시간 (200 ms)과 고장 대응의 시간 예산을 같은 이름으로 부르지 않는다. 예산의 합이 `SG-01`의 시간보다 작아야 한다는 관계만 적는다. "운전자의 요구보다 큰 가속"은 고장이 없을 때 같은 입력에서 나오는 가속과의 차이로 정의한다 | FuSa |
| I8 | test를 두 수준으로 나눈다: 소프트웨어 요구사항 수준 (출력과 구동 허용 신호가 바뀌는 주기)과 차량 수준 (가속의 차이). 차량의 질량과 저항은 가정으로 표에 둔다 | 임베디드 |
| I9 | 단계 1의 safety case에서 "감시 자신의 고장" 가지를 아직 논증하지 않은 것으로 그리고, `SG-01`의 논증이 단계 1에서 닫히지 않았다고 본문에 적는다 | FuSa |
| I10 | `FI-01`의 기대에 "판정 전에도 출력은 낮은 채널을 따르므로 초과가 없다"를 넣는다. `FI-04`의 기대에 "5주기 뒤에 고정"을 넣는다 | 둘 다 |
| I12 | CAN 지연, 구동 허용 신호의 지연, inverter의 응답을 plant model의 parameter로 둔다. "실행 시간 0"은 "sim이 못 보이는 것" 표에 적는다 | 둘 다 |

## 답하는 형식

- I7 수정안에 "동의" 또는 "반대"를 적는다. 반대면 고칠 문장을 적는다.
- 받아들인 조건 가운데 상대가 낸 것에 반대하는 것이 있으면 적는다.
- 20줄을 넘기지 않는다. 이번이 마지막 회다. 합의되지 않은 것은 진행자의 안으로 진행하고 저자에게 쟁점으로 알린다.
