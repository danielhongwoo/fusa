- 쓴 사람: 진행 (Claude 주 세션). 날짜: 2026-11-23.
- 2차의 판정: FuSa 통과 (새 지적 B 1, C 2), 임베디드 조건부 통과 (새 지적 B 1, C 4). 1차의 지적은 F-21 하나를 빼고 모두 닫혔다.
- 이 반영은 검토자가 다시 보지 않았다. 임베디드 검토자가 조건으로 건 E-11은 검토자가 적은 방법 그대로 고쳤고, 검토자가 재현한 변이 (배열 뒤에 필드를 더한다)를 변이 목록에 넣어 build가 잡는 것을 확인했다.

## 임베디드 엔지니어의 2차 지적

| 지적 | 등급 | 한 일 |
|---|---|---|
| E-11 "배열은 구조체의 끝에 둔다"는 약속을 지키게 하는 것이 주석뿐이다 | B | 받아들였다. 세 구조체에 `_Static_assert` (배열의 끝이 구조체의 끝이다)를 두었다 (`flow.c`, `pedal_check.c`, `inverter_check.c`). 배열 뒤에 필드를 더하는 변이 셋을 변이 목록에 넣었고, build가 잡는 것으로 센다. test-report 5절과 13장에 적었다 |
| E-12 `pedal_check_t`와 `inverter_check_t`의 한 칸 넘는 쓰기를 test가 값으로 잡지 않는다 | C | 받아들였다. unit test에서 배열을 가진 상태를 구조체 바로 뒤에 값을 둔 틀에 넣고 그 값을 본다 (`TC-014`, `TC-020`, `TC-021`, `TC-022`). 고치다가 알게 된 것이 있다. 검사를 더하자 (TC-014의 guard, TC-021의 열거) 페달 검사와 실행 확인의 범위 변이에서 unit test가 값으로 실패를 알린 뒤 끝나지 않았다. 넘는 쓰기가 test 함수의 stack에 있는 반복문의 변수를 덮어썼기 때문이다. 변이 도구는 300초의 시간 한계로 "잡음"이라고 셌을 것이다. 검토자가 본 `Abort trap`과 같은 뿌리다 (stack에 떨어지는 쓰기). 상태를 틀에 넣은 지금은 값으로 실패하고 바로 끝난다 (변이 아홉 개를 다시 넣어 11초). `make check`에 sanitizer를 넣는 것은 하지 않았다 (아래) |
| E-13 `proof_mutation.py`가 도구의 실패를 "잡음"으로 센다 | C | 받아들였다. `prove.sh`가 증명의 실패 (`VERIFICATION FAILED`)와 도구가 판정을 내지 못한 것을 다른 줄로 내고, `proof_mutation.py`는 뒤의 것을 오류로 센다 |
| E-14 따로 둔 변이의 이유가 "우연히 같은 조합이 있다"를 아직 적는다 | C | 받아들였다. 검토자의 계산을 unit test로 옮겼다 (`TC-021`: 표시 1, 2, 3의 모든 열을 일곱 개까지, 모든 질문의 번호에서 센다. 틀린 열이 옳은 답을 내는 경우 0). 이유를 "닿을 수 있는 상태에서는 동등하다. memory가 망가진 경우에는 이 줄이 마지막 보호다"로 고쳤다 (변이 도구, test-report 7절, TSC 9.1절) |
| E-15 작은 것 둘 | C | 받아들였다. `SWR-26`의 `verified_by`에 `TC-011`. `flow.c`에 `_Static_assert(FLOW_TASK_COUNT == 3u)` |

## 하지 않은 것

- `make check`에 AddressSanitizer를 넣는 것 (E-12의 "더 나은 방법"). 검토자는 복사본에서 ASan이 `TC-021`의 변이를 잡는 것을 확인했다. 넣으면 세 구조체와 앞으로 더할 것을 한꺼번에 덮는다. 이번에는 값으로 보는 검사 셋과 compile할 때의 확인으로 닫고, sanitizer로 test를 돌리는 것은 묶음 4 (15, 16장: 동적 분석)에서 예제에 넣을지 정한다.
